# 发版任务业务描述

`准备发布`创建或复用`【发版】`任务时，任务描述只服务业务阅读。关系清单、A/B/C/D JSON、哈希、幂等键、流水线原始字段和证据对象不得进入描述，也不得再尝试用 HTML 注释隐藏；云效 Markdown 会把这类注释按文本展示。

## 可见更新日志

正文固定使用：

```text
<产品名称><版本>更新日志：

【新功能】
1「模块」具体变化，涉及角色可完成的业务结果

【Bug修复】
2「模块」修复或优化的异常，涉及角色恢复的业务结果
```

规则：

1. 标题从迭代名称、迭代描述和项目产品名称自动生成。优先使用迭代中明确记录的对外产品版本；没有独立产品版本字段时，将`ONEOS_V1.4.1`规范化为`OneOS PC版V1.4.1更新日志：`，不得凭空改版本。
2. 按`新功能`、`Bug修复`两组展示；没有内容的组不输出。
3. 两组共用连续序号，格式为`1「模块」...`，不输出需求、交付、测试或Bug编号。
4. 每项只写一段，顺序为“模块 + 用户可感知变化 + 适用角色/部门 + 业务价值”。
5. 同一模块的多个细碎Bug可合并为一项；不同业务目标不得强行合并。
6. 删除“已完成、测试完成、ASSOCIATED、A类、范围哈希、幂等键”等内部术语。
7. 自动读取每个A类需求和纳入Bug的标题、完整描述、验收标准、模块、标签、类型、角色/部门和正式关联，不得只根据标题生成。
8. A类需求及类型为新增/优化的变化归入`新功能`；正式Bug和明确以修复异常为目标的事项归入`Bug修复`。类型/标签优先于关键词判断。
9. 同一模块、同一业务目标的多个Bug可合并，但必须在受管评论账本中保留全部源ID；需求和Bug若内容不同不得为减少条数而合并。
10. 缺少角色或价值依据时只写可验证变化，不得猜测；描述信息不足时回退到清理后的工作项标题，而不是输出技术字段。
11. 使用`formatType=MARKDOWN`和真实换行写入；禁止把整篇描述压成一行。
12. 写入后回读并检查：标题存在、分组独立成行、序号连续、每个A类需求至少覆盖一次、纳入Bug已覆盖或明确合并，且正文不含 HTML 注释、受管标记或技术JSON。

## 受管评论账本

机器追溯数据写入发版任务的独立评论，不写入描述。评论固定以`【发布受管数据】`开头，后接单行 JSON：

```text
【发布受管数据】{"schemaVersion":"oneos.release-batch/v2","scopeHash":"...","releaseNoteItems":[{"number":1,"sourceIds":["REQ-1"]}],"idempotencyKey":"...","generatedAt":"..."}
```

账本规则：

- 创建发版任务的同一事务必须同时创建绑定`${action.N.id}`的首条受管评论。
- 评论接口不支持更新，因此账本只追加、不覆盖。完全相同的`idempotencyKey`和载荷不得重复创建；载荷变化时追加新记录并保存`previousCommentId`。
- 读取时只接受`schemaVersion=oneos.release-batch/v2`、`scopeHash`和`idempotencyKey`齐全的记录；按官方评论时间选择最新有效记录，并再次核对正式关系和当前任务状态。
- 描述更新只替换业务更新日志，保留其他人工内容；账本更新只追加新评论，不修改已冻结范围、正式关系、流水线或发布尝试。
- 已存在生产尝试时，只允许修正文案；任何范围或账本范围变化继续阻塞。
- 历史任务若仍在描述中包含旧 HTML 受管块，先解析并迁移为受管评论，官方回读评论成功后再从描述删除；不得先删后存。

## 重整已有描述

`准备发布`重复执行时必须复用同一发版任务。若范围哈希一致，重新读取当前标准迭代或例外来源范围中的需求和Bug，重新生成业务更新日志并回读；受管载荷未变化时复用最新账本记录，变化时追加一条新记录。不创建新任务、不重建关系、不启动生产，也不读取或启动测试流水线。

口令始终是：

```text
$yunxiao-release-operations
准备发布：迭代=<精确名称>
```
