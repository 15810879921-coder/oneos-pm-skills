# 测试交接与发布修复回流

## 正常需求提测

当前开发任务取得可信交付版本后，必须立即创建或复用其唯一正式【测试】任务；`formal-plan`与`mandatory-test-task`都不得等待同需求的兄弟开发任务。普通模式使用已合并版本；隔离快速模式使用`oneos.rapid-delivery/v1`记录的远端源提交。

1. 开发侧必须完成并回读本范围的`【代码交付记录】`：仓库、源/目标分支、提交 SHA、MR 编号/URL、MR 状态、合并时间和交付版本。
2. 创建/复用【测试】后，回读`TASK_SUB→【交付】`、`ASSOCIATED→需求`、唯一测试主管负责人和`oneos.test-scope/v1`。端标签必须是`Web`或`小程序`；混端或无端标签仅阻塞范围归属，不以流水线为由阻塞。
3. 向`$YunxiaoQA`交接当前端侧范围、测试建议和开发版本。未发现迭代、测试流水线或`oneos.test-deployment/v1`时，仍可开始测试；在交接中列为`测试部署待补`，不得伪造部署结果。
4. 测试流水线不是本交接节点的自动动作；如需运行，只能由授权的显式流水线命令处理。**小程序**不启动云效测试流水线。

## 发布/验收失败开发回流

```text
$yunxiao-development-delivery
处理发布回流：发版任务=TASK-900
```

1. 精确读取发版任务的生产事件或产品验收不通过证据、回滚状态、受影响需求和迭代。
2. 只接受YunxiaoQA已建立且带同一回流批次ID的Bug；若没有正式Bug，零代码写入并交回`接收发布回流`。
3. 冻结当前开发可处理Bug集合，按现有批量修复规则修改、验证并按仓库+分支统一提交；保留逐Bug代码归属。
4. 所有分组合并后：**Web**按涉及仓库执行各自已创建的test流水线；相同流水线去重后只执行一次，并以组合证据证明部署版本覆盖全部回流修复。**小程序**跳过test流水线，在回流交接中注明`testPipeline=skipped`。
5. 将每个成功包含的Bug改为`已修复`，保持验证者不变；不关闭Bug、不写复测通过。
6. 输出：

```text
$YunxiaoQA
验证发布回流：发版任务=TASK-900；缺陷=BUG-1,BUG-2；回归证据清单=<JSON文件>
```

开发侧不得直接调用`重新发布`，不得把原生产回滚成功当成修复成功，也不得修改需求、交付或产品验收状态。
