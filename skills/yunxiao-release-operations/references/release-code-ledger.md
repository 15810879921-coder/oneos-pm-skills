# 发布代码清单补录

## 目标

本清单只适用于 **Web**。Web 的`准备发布`必须为本批每个 A 类需求及纳入 Bug 取得可追溯的远端代码锚点。优先复用事项评论中的 `【代码交付记录】`；评论缺失或字段不完整时，主动通过正式关系和官方 Codeup CLI 反查并补录，不要求开发人员手工回填。**小程序**不要求、查询、补录或阻塞于云效/Codeup 代码锚点；其代码发布链路不可由云效观测时记录`codeTrace=external_unmanaged`即可。

## Web 每个事项的处理顺序

1. 读取该事项全部 `【代码交付记录】` 评论；只接受可唯一对应的仓库、源分支、目标分支、提交ID或 MR。
2. 评论完整时，实时回读 Codeup 仓库、分支、MR、提交和合并状态，确认评论没有过期。
3. 评论缺失或不完整时，沿事项的正式代码资产、需求/开发任务/交付关系和已关联 MR/分支反查；再用官方 Codeup CLI 读取远端分支、MR 和提交。标题相似、分支名称猜测或纯语义匹配不得单独建立关联。

### 无代码评论时的强制代码侧发现

在结论为“代码锚点无法唯一确认”之前，必须完成以下只读发现，不能等待用户提示：

1. 逐页读取项目 Codeup 仓库至空页；按事项精确编号查询候选 Web 仓库的分支、MR 与提交历史，所有列表均翻页至空页。事项编号出现在分支名、MR 标题或提交信息中只可作为候选线索，不能单独作为代码归属。
2. 对每个候选分支读取其提交历史，不能只看当前 HEAD：同名分支可能已继续承载其他事项。逐个读取命中事项编号的提交，并检查其变更文件树是否与工作项的模块和问题现象一致。
3. 只有“精确提交编号 + 变更树 + 工作项范围”三者一致时，才确认仓库与代码锚点；随后读取目标生产分支及完整 Flow 生产流水线清单，以仓库、目标分支、部署目标唯一确定组件。候选提交找不到、多个提交均匹配或变更树与事项不符时，才报告无法唯一确认，并列出已检查的候选。
4. 命中提交所在分支若含后续范围外提交，不得将当前分支 HEAD 或整支分支作为发布源。冻结该精确提交，并以目标生产分支为基线重放该提交的精确补丁，生成`release/<发版任务ID>-...`干净候选；候选只允许`codeup-commit-multiple-files`的`create/update`动作，且必须在创建 MR 前比对精确提交变更树，不得带入原分支其他提交。仅在分支已删除且可从已合并 MR 的补丁集精确恢复时，才按下文“源分支已删除”规则恢复临时分支。
5. 当尚无生产尝试而准备发布重复执行、或新纳入的Bug改变发布范围时，对全部冻结 Web 事项重新构建组件矩阵；不得把新事项只写入隐藏范围而保留旧矩阵。
6. 对所有 Web 源交付和纳入Bug生成`releaseCodeItems`、逐事项`codeAnchors`与组件矩阵，运行`skill-run validate_release_component_matrix.py --input <matrix.json>`。结果必须同时满足：每个事项至少一个锚点、每个锚点落入一行组件、每行组件的`sourceItemIds`与锚点一致、每个组件唯一映射逻辑`prod`流水线。校验返回`blocked`时禁止只发布已识别仓库。

仅当仓库、源分支、目标分支以及至少一个提交ID或 MR 可唯一验证时，创建并回读一条补录 `【代码交付记录】` 评论：

```text
仓库：<名称或URL>
源分支：<分支>
合并目标：<目标分支>
提交ID：<SHA，多个用逗号分隔>
MR：<编号/URL/当前状态>
需合并分支：<源分支> → <目标分支>
采集方式：准备发布补录
核验时间：<Asia/Shanghai 精确时间>
```

测试/生产流水线字段仍是可选信息：能唯一定位时补充，不能定位时省略，不写“未配置”。

零候选、多候选、跨项目、分支已删除且无可验证MR/提交、或评论与远端事实冲突时，不得补录为成功。记录 `【代码交付核验失败】` 评论（事实、候选、原因、时间），并将该事项列为发布代码清单阻塞项。

## 合并到生产目标分支

当本次 Web 发布要求合并代码时，必须先按每个仓库的正式 MR、补丁集和提交记录确定“源提交 → 目标分支”，再执行合并：

1. 先读取目标分支 HEAD、源分支 HEAD，以及不存在进行中同源/同目标 MR；禁止把 `dev` 当作默认可合并源分支。
2. 源分支已删除时，可通过该事项已合并 MR 的 `MERGE_SOURCE` 补丁集提交恢复**临时候选分支**，但恢复前后均要记录原 MR、提交 SHA 和目标分支；无法证明候选提交只覆盖本次范围时停止，不得用整个 `dev` 替代。
3. 创建候选 MR 后，读取其 `ahead`、`behind`、冲突状态、检查项和变更范围。出现本次范围外提交、无法解释的大量 ahead、冲突、未通过的强制检查或目标分支漂移时，不得自动合并，列为“待定范围合并”并保留 MR 证据。
4. 仅在候选 MR 的源/目标、提交范围和合并策略均已确认时，执行一次非强制合并，读取 `MERGED` 状态与目标分支新 SHA；合并后才允许触发该仓库对应的生产流水线。

“分支仍存在”不等于“该分支只含本次代码”；“任务标题相同”也不等于可将整支集成分支合入生产分支。生产目标分支必须从官方 Codeup/Flow 配置唯一验证并冻结，不得硬编码为`master`。

## 多项目组件矩阵（Web）

在写入`【发布代码清单】`前，按每条A类需求、纳入Bug及其源交付汇总全部**不同仓库**，形成一行一个“仓库 + 目标分支 + 部署目标”的组件矩阵。每行至少包含来源工作项、仓库ID/URL、源分支、目标分支、提交或已合并MR、组件名、生产流水线ID/名称和逻辑`prod`环境。

- 逐仓库从正式关系、已回读代码交付记录和官方 Codeup CLI 反查；标签`Web`只表示端别，绝不表示仓库或流水线。
- 每个仓库必须唯一映射到活动生产流水线；可共享同一流水线的多个仓库按流水线ID去重后并行提交一次，但仍保留每个来源事项到该执行ID的映射。
- `ln-cloud`必须按实际变更路径映射到对应模块流水线，不得启动全仓或不相关模块流水线。
- 零映射、多映射、缺少仓库、缺少目标分支、缺少部署目标或遗漏任一代码变更仓库，均阻止**整个**Web发版执行；不得只发布可识别的前端组件。
- 用户明确列出的单个Bug可标记`codeAnchorWaived=true`，但该豁免只允许保留该Bug在已有组件行中；不能用来删除其组件、替代仓库识别，或放宽其他事项与所有组件的矩阵完整性。

## 发布清单与执行

Web 的准备发布只在每个选入事项都有已回读的代码交付记录、且组件矩阵完整后，创建/更新 `【发版】`任务的 `【发布代码清单】` 评论。清单逐项保留来源事项、仓库、源/目标分支、提交、MR、合并状态、组件和唯一生产流水线。小程序不创建该清单，也不因缺少其字段而阻塞。

Web 的执行发布必须重新运行组件矩阵校验并做最小实时复核；它不得把清单第一行或前端流水线当作默认执行集合。对校验结果中的全部不同流水线ID并行启动或接续一次执行，并在同一发布尝试中保存全部组件执行ID。用户明确声明`流水线发布已人工操作`时不再启动流水线，只能按组件唯一绑定已有成功执行。范围/正式关系变化时停止并要求重新`准备发布`；范围未变、尚无生产尝试且仅旧矩阵漏记已在范围内的代码仓库时，先自动完成代码侧反查、修正受管矩阵并回读，再继续执行。小程序不消费或复核该清单。
