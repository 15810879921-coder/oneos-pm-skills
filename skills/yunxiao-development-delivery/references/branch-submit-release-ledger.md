# 分支、提交与发布清单记录

## 适用口令

- `开始开发:任务=<开发任务编号>`：只建立开工追溯。
- `开始修复bug:<BUG-ID>`：只建立 Bug 开工追溯。
- `提交代码`：受控提交当前工作区代码。
- `完成开发:任务=<开发任务编号>`、`完成修复bug:<BUG-ID>`：复核并写入完成记录。
- `修复bug:<BUG-ID>`：一键顺序执行开始修复、修复和本地验证、提交代码、完成修复。

## 开始记录

先解析唯一事项、仓库和分支；创建/复用分支并回读其唯一归属后，创建一条 `【研发启动】` 评论：

```text
事项：<开发任务或BUG编号>
开发需求快照：<sha256；Bug不适用时写不适用>
开始时间：<Asia/Shanghai 精确时间>
仓库：<名称或URL>
分支：<分支名>
操作者：<当前账号>
启动方式：正常|一键修复
依赖指纹：<摘要>
运行时：<Node/pnpm 或 JDK/Maven 实际版本>
缓存目录：<动态解析结果；未解析时写未解析>
依赖策略：直接复用|本地仓库复用|pnpm store 离线复用|增量安装
网络下载：否
回退原因：<无|锁文件变化|运行时不一致|缓存缺失|校验失败>
```

分支无法安全创建/复用、归属不唯一或被其他事项占用时停止开工状态流转。按[本机依赖复用](dependency-reuse.md)完成动态发现前，不得写启动评论；开始节点只记录策略，`网络下载`固定为`否`。需求/开发任务的代码资产关联失败仅记为追溯待补，不阻断开工、代码验证或后续受控提交。`【研发启动】`评论无法回读时，不得伪造开始记录；继续代码实现并标记`启动/工时证据待补`，只跳过无法审计的实际工时写回，不阻断既有代码交付复验、当前任务关单或测试范围交接。重试复用同一事项和分支时不得重复写首次开始时间。

## 提交代码：先核对，再写入

提交、推送、创建/更新MR、可能触发的 Maven API SNAPSHOT 预发布及`【代码交付记录】`均不得读取、要求、写入或以开发任务/MR的`sprint`字段推断迭代。迭代可能在后续由源`【交付】`正式关联；测试流水线只在`准备发布`或已有 Bug 测试部署节点处理。

提交前只读收集本地 `仓库、当前分支、HEAD、脏文件摘要、拟提交说明、已有MR`，并读取云效事项及其已有受管评论。

自动提交必须同时满足：

1. 当前分支可唯一关联到同一开发任务或 Bug；
2. 改动摘要与事项标题/描述不冲突；语义匹配只作补偿，不得单独作为自动提交依据；
3. 事项处于可开发状态，且没有其他事项已占用该分支的受管记录。

通过时，先创建本地 commit。若当前变更命中[API包受控预发布](api-artifact-publish.md)，必须在 push 前完成受控 SNAPSHOT deploy、消费者重新解析和`【API包发布记录】`回读；发布失败时不 push、不创建/更新MR，也不触发依赖该包的流水线。未命中时按原顺序执行 push、创建或更新 MR。随后在**对应开发任务或 Bug 评论**追加 `【代码交付记录】`：

```text
仓库：<名称或URL>
源分支：<分支>
合并目标：<目标分支>
提交ID：<SHA，多个用逗号分隔>
MR：<编号/URL/当前状态>
合并时间：<Asia/Shanghai 精确时间；未合并写待合并>
交付版本：<合并提交SHA或已核验远端源提交>
需合并分支：<源分支> → <目标分支>
测试流水线（可选）：<名称/ID/URL；环境；结果>
生产流水线（可选）：<名称/ID/URL；环境；本次是否需执行>
记录时间：<Asia/Shanghai 精确时间>
```

流水线字段只能在可唯一定位时填写；无法读取、多个候选或当前不适合查询时直接省略，不写“未配置”。

`【API包发布记录】`的字段、一次提交一次记录的幂等键、消费者重新解析和流水线 SNAPSHOT 刷新门禁均以[API包受控预发布](api-artifact-publish.md)为准。它只记录测试 SNAPSHOT 包发布事实；不得把它写成生产发布、release 包发布或流水线成功证据。

任一核对不通过时，禁止提交、推送、MR 或云效写入；输出“本地代码信息 / 云效候选事项 / 不一致原因”，等待开发人员明确输入 `确认关联：<事项编号>`。确认后重新读取工作区和云效快照；任何漂移都要求重新确认。

## 完成记录与一键修复

完成口令先检查未提交改动、提交ID、MR、分支关联及可用验证证据。仍有未提交代码时转入同一受控提交核对；不一致仍必须停下确认。MR 合并成功后必须更新并回读同一`【代码交付记录】`的 MR 状态、合并时间和交付版本；普通模式缺任一项不得将开发任务标记完成。通过后追加 `【研发完成】`评论，记录完成时间、仓库、分支、提交ID、MR和验证结果；测试流水线不属于本节点。

`完成修复bug` 只在证据齐全后把 Bug 置为 `已修复` 并交测试复测；不得关闭 Bug 或改写验证者。`修复bug` 一键路径在任何阶段遇到分支/事项不一致时，停在该阶段等待确认，确认后从最近已回读检查点续跑。

## 发布使用方式

`准备发布`读取本次范围内任务/缺陷的 `【代码交付记录】` 评论，汇总已有仓库、源/目标分支、提交、MR 和可选流水线信息到 `【发版】`任务的 `【发布代码清单】` 评论。评论仅缩短范围收集，不替代正式关系和实时 Codeup/Flow 回读。

`执行发布`直接消费冻结的发布代码清单，不重复全量搜寻；仅复核其中分支、提交、MR、流水线和目标环境是否仍一致。缺失的可选流水线信息可实时补查，但评论缺失本身不得阻塞准备发布。
