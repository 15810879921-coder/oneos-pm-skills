# 分支、提交与发布清单记录

## 适用口令

- `开始开发:任务=<开发任务编号>`：只建立开工追溯。
- `开始修复bug:<BUG-ID>`：只建立 Bug 开工追溯。
- `提交代码`：受控提交当前工作区代码。
- `完成开发:任务=<开发任务编号>`、`完成修复bug:<BUG-ID>`：复核并写入完成记录。
- `修复bug:<BUG-ID>`：一键顺序执行开始修复、修复和本地验证、提交代码、完成修复。

## 开始记录

先解析唯一事项、仓库和分支；创建/复用分支并回读关联成功后，才创建一条 `【研发启动】` 评论：

```text
事项：<开发任务或BUG编号>
开始时间：<Asia/Shanghai 精确时间>
仓库：<名称或URL>
分支：<分支名>
操作者：<当前账号>
启动方式：正常|一键修复
```

分支创建、关联或评论回读失败时停止开工状态流转。重试复用同一事项和分支时不得重复写首次开始时间。

## 提交代码：先核对，再写入

提交前只读收集本地 `仓库、当前分支、HEAD、脏文件摘要、拟提交说明、已有MR`，并读取云效事项及其已有受管评论。

自动提交必须同时满足：

1. 当前分支可唯一关联到同一开发任务或 Bug；
2. 改动摘要与事项标题/描述不冲突；语义匹配只作补偿，不得单独作为自动提交依据；
3. 事项处于可开发状态，且没有其他事项已占用该分支的受管记录。

通过时，才执行原生 `commit/push`，创建或更新 MR，并在**对应开发任务或 Bug 评论**追加 `【代码交付记录】`：

```text
仓库：<名称或URL>
源分支：<分支>
合并目标：<目标分支>
提交ID：<SHA，多个用逗号分隔>
MR：<编号/URL/当前状态>
需合并分支：<源分支> → <目标分支>
测试流水线（可选）：<名称/ID/URL；环境；结果>
生产流水线（可选）：<名称/ID/URL；环境；本次是否需执行>
记录时间：<Asia/Shanghai 精确时间>
```

流水线字段只能在可唯一定位时填写；无法读取、多个候选或当前不适合查询时直接省略，不写“未配置”。

任一核对不通过时，禁止提交、推送、MR 或云效写入；输出“本地代码信息 / 云效候选事项 / 不一致原因”，等待开发人员明确输入 `确认关联：<事项编号>`。确认后重新读取工作区和云效快照；任何漂移都要求重新确认。

## 完成记录与一键修复

完成口令先检查未提交改动、提交ID、MR、分支关联及可用验证证据。仍有未提交代码时转入同一受控提交核对；不一致仍必须停下确认。通过后追加 `【研发完成】` 评论，记录完成时间、仓库、分支、提交ID、MR、验证结果和可选流水线信息。

`完成修复bug` 只在证据齐全后把 Bug 置为 `已修复` 并交测试复测；不得关闭 Bug 或改写验证者。`修复bug` 一键路径在任何阶段遇到分支/事项不一致时，停在该阶段等待确认，确认后从最近已回读检查点续跑。

## 发布使用方式

`准备发布`读取本次范围内任务/缺陷的 `【代码交付记录】` 评论，汇总已有仓库、源/目标分支、提交、MR 和可选流水线信息到 `【发版】`任务的 `【发布代码清单】` 评论。评论仅缩短范围收集，不替代正式关系和实时 Codeup/Flow 回读。

`执行发布`直接消费冻结的发布代码清单，不重复全量搜寻；仅复核其中分支、提交、MR、流水线和目标环境是否仍一致。缺失的可选流水线信息可实时补查，但评论缺失本身不得阻塞准备发布。
