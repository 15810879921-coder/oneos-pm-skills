# 生产后产品验收

## 口令

```text
/skill YunxiaoPM
拉取待验收需求：发版任务=TASK-900

/skill YunxiaoPM
验收通过：发版任务=TASK-900；验收人=王经理；证据=ACCEPTANCE-ID或URL

/skill YunxiaoPM
验收不通过：发版任务=TASK-900；验收人=王经理；原因=...；证据=ID或URL
```

`发版任务`是唯一锚点；不接受单个需求编号替代，不按标题猜范围。

## 通过门禁

1. 发版任务唯一且状态=`发布完成`。
2. 其受管生产证据区块符合`oneos.release-production/v1`字段口径：`pipelineStatus=成功`、环境=`prod`、回调已验签、生产验证=`通过`，执行ID、生产验证计划、验证证据、完整观察时间、幂等键和不可变生产锚点均非空。
3. 正式关联的本批需求全部=`发布完成`，与生产证据scope完全一致。
4. 每个需求唯一关联一个源`【交付】`，交付保持=`处理中`。
5. 验收人、证据非空，证据对应本批生产版本和验收范围。
6. 先dry-run并经YunxiaoPM Plan确认。

执行入口：

```powershell
skill-run accept_release.py pass `
  --release-id <云效内部ID> `
  --release-sn TASK-900 `
  --acceptor '王经理' `
  --evidence 'ACCEPTANCE-ID-or-URL' `
  --dry-run
```

去掉`--dry-run`后，脚本先向发版任务、每条需求和每个【交付】写入同一`oneos.product-acceptance/v1`验收区块并回读，再依次推进本批需求`发布完成→已完成`、对应`【交付】处理中→已完成`、发版任务`发布完成→已完成`。每个对象均按真实下一状态动态解析，不使用本地硬编码ID。

## 验收不通过

```powershell
skill-run accept_release.py fail `
  --release-id <云效内部ID> `
  --release-sn TASK-900 `
  --acceptor '王经理' `
  --evidence 'ACCEPTANCE-ID-or-URL' `
  --reason '验收失败原因' `
  --dry-run
```

确认后向发版任务、需求和交付写入并回读统一“不通过”证据；尝试把发版任务从`发布完成`转到项目真实`发布失败`，若流程不支持则保留实际状态并在证据中标记`notSupported`。需求保持真实状态、交付保持`处理中`，不得伪装为生产流水线失败，也不得擅自回退需求。

无论状态迁移是否受项目流程支持，下一步都固定输出：

```text
/skill YunxiaoQA
接收发布回流：发版任务=TASK-900；触发=产品验收失败；证据=ID或URL
```

后续必须经过正式缺陷、开发修复、test部署、逐Bug复测和回归证据，再由发布Skill执行`重新发布`；不得直接再次验收或直接重跑生产。

## 幂等与部分失败

- 幂等键=`发版任务内部ID + 生产执行ID + 验收结论 + 验收证据`。
- 重试只替换同一受管验收区块，保留人工描述。
- 首次执行先把同一验收幂等键写入发版任务、全部需求和全部交付，再逐项流转；任一状态写入失败时停止并逐项报告真实状态。
- 续跑允许需求处于`发布完成|已完成`、交付处于`处理中|已完成`、发版任务处于`发布完成|已完成`；已经完成的对象必须带同一验收幂等键，否则拒绝接续。
- 重试只流转尚未完成的对象，发版任务最后关闭；禁止用浏览器补点剩余对象。
- 发版任务已完成时，只有全部需求、交付和验收证据均一致才按幂等成功返回。
