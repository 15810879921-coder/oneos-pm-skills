# 发版任务业务描述

`准备发布`创建或复用`【发版】`任务时，描述必须先服务业务阅读，再保存机器受管数据。禁止把关系清单、A/B/C/D JSON、哈希、幂等键、流水线原始字段或证据对象直接堆在可见正文中。

## 可见更新日志

正文固定使用：

```text
<产品名称><版本>更新日志：

【新功能】
1「模块」具体变化，涉及角色可完成的业务结果

【Bug修复】
2「模块」修复或优化的异常，涉及角色恢复的业务结果
```

规则：

1. 标题从迭代名称、迭代描述和项目产品名称自动生成。优先使用迭代中明确记录的对外产品版本；没有独立产品版本字段时，将`ONEOS_V1.4.1`规范化为`OneOS PC版V1.4.1更新日志：`，不得凭空改版本。
2. 按`新功能`、`Bug修复`两组展示；没有内容的组不输出。
3. 两组共用连续序号，格式为`1「模块」...`，不输出需求、交付、测试或Bug编号。
4. 每项只写一段，顺序为“模块 + 用户可感知变化 + 适用角色/部门 + 业务价值”。
5. 同一模块的多个细碎Bug可合并为一项；不同业务目标不得强行合并。
6. 删除“已完成、测试完成、ASSOCIATED、A类、范围哈希、幂等键”等内部术语。
7. 自动读取每个A类需求和纳入Bug的标题、完整描述、验收标准、模块、标签、类型、角色/部门和正式关联，不得只根据标题生成。
8. A类需求及类型为新增/优化的变化归入`新功能`；正式Bug和明确以修复异常为目标的事项归入`Bug修复`。类型/标签优先于关键词判断。
9. 同一模块、同一业务目标的多个Bug可合并，但必须在隐藏追溯数据中保留全部源ID；需求和Bug若内容不同不得为减少条数而合并。
10. 缺少角色或价值依据时只写可验证变化，不得猜测；描述信息不足时回退到清理后的工作项标题，而不是输出技术字段。
11. 写入后回读并检查：标题存在、分组正确、序号连续、每个A类需求至少覆盖一次、纳入Bug已覆盖或明确合并、正文没有技术JSON。

## 受管数据

技术数据保留在正文末尾的纯HTML注释中，不使用可见`<pre>`：

```html
<!-- YUNXIAO_RELEASE_BATCH_START
{"schemaVersion":"oneos.release-batch/v2","scopeHash":"...","releaseNoteItems":[{"number":1,"sourceIds":["REQ-1"]}],"idempotencyKey":"..."}
YUNXIAO_RELEASE_BATCH_END -->
```

更新描述时：

- 只替换业务更新日志区和本Skill拥有的受管注释。
- 保留任务中的其他人工内容。
- 不改变已冻结范围、正式关系、流水线或发布尝试账本。
- 已存在生产尝试时，只允许修正文案，不得借此增删发布范围。

## 重整已有描述

`准备发布`重复执行时必须复用同一发版任务。若范围哈希一致，重新读取当前迭代范围中的需求和Bug，重新生成业务更新日志并回读，不创建新任务、不重建关系、不启动生产。

口令始终是：

```text
$yunxiao-release-operations
准备发布：迭代=<精确名称>
```
