# 执行顺序与回读

本 Skill 的真实云效操作只通过官方 `aliyun devops` CLI 和自带 `yunxiao_cli_gateway.py` 执行。浏览器、视觉点选、截图/OCR、DOM、Cookie、连接器和网页内部接口均禁止，CLI 缺失或受限时停止并报告。

## 写入顺序

每个写事务固定按以下顺序执行：

1. `doctor`校验 CLI、devops 插件、本机认证环境变量和当前 PAT 用户。
2. 通过 CLI 读取精确任务、关系、范围、流水线、环境、当前执行和幂等账本；涉及发版任务时还必须读取并核验其为顶层任务、与迭代/A类需求/多个源【交付】及无关联单据已完成Bug的正式关联一致，拒绝任何`TASK_SUB→【交付】`父子关系。
3. 生成带稳定业务键的事务计划；守卫包含全部写入前置状态，动作只包含本口令授权的精确写入，验证只回读受影响对象。
4. `preflight`执行只读守卫并保存完整 JSON 哈希。
5. `apply`重新读取守卫；任何漂移都零写入。未漂移时动作只执行一遍。
6. 定向回读任务状态、关系、执行 ID、运行状态、环境、版本和证据；成功回执写入幂等账本。
7. 相同事务重试直接返回成功账本，不重新提交流水线、发布或回滚。

状态动作拆成三步：先保存证据，再写目标状态，最后聚合回读。任一步失败都返回真实部分状态，不得用预期值补齐。

## 流水线与发布执行

- 启动前使用 `flow-list-pipelines`/`flow-get-pipeline` 或对应 AppStack 读取命令解析名称、原始环境、仓库、分支、参数和触发模式；先排除禁用、归档及名称带`-old/_old/-legacy/_legacy/旧/停用/废弃/归档`的退役定义，再对活动候选做唯一性判断。Flow原始`envName=日常环境`不单独否定由名称、代码源/分支和部署目标共同确认的生产逻辑环境。
- 启动使用白名单 `flow-create-pipeline-run` 或精确 AppStack 研发阶段执行命令，并立即保存新执行 ID。
- 通过 `flow-get-pipeline-run`、任务/步骤/日志读取命令或对应 AppStack 命令定向轮询；间隔不超过 60 秒并同步进度。
- 失败时读取第一个失败阶段、任务、步骤和脱敏日志。日志不可读时返回真实权限或过期边界。
- 人工卡点只在用户口令明确授权且当前执行确实等待该卡点时使用 CLI 通过/拒绝命令；OTP、权限提升和未提供的必填参数继续阻塞。
- 不修改流水线定义、变量组、服务连接、保护规则或发布验证阈值。

## 回调

正常 CLI 主动轮询不要求回调证据，以实时执行回读作为依据。只有实际收到回调并准备由回调驱动状态写入时，才必须先由 `verify_release_callback.py`校验签名、时间戳、执行 ID、环境、范围、当前状态、幂等键和重放保护，再进入 CLI 事务预检。回调验证成功不等于允许跳过实时状态回读。
