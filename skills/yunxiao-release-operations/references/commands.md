# 发布运维七条口令

本文件七条口令中的全部云效 Projex、Flow、Codeup 和 AppStack 读取与写入只通过官方 `aliyun devops` CLI 及 `yunxiao_cli_gateway.py` 执行。浏览器、视觉点选、DOM、Cookie、连接器和网页内部接口均不是执行或回退通道。

## 通用格式

每次先显式启用：

```text
/skill yunxiao-release-operations
```

下一行输入业务口令。字段之间使用空格，不需要分号。

## 附：受限模拟生产冒烟（仅显式授权时）

当用户明确要求“从既有测试流水线复制一个副本，在测试环境模拟生产”时，先执行受限设置动作，再运行副本；如果 CLI 无法解析源流水线已用的构建组，则不创建副本，改为把既有测试流水线运行一次，并将结果标记为 `releaseMode=smoke`。

- 仅允许源流水线为日常环境、名称含 `test`；副本名称必须同时含 `smoke` 和 `prod`，且绝不能是实际 `prod` 流水线。
- 不创建 Runner、主机组、服务连接、容器、部署目标或 Webhook；移除通知插件；仅手工触发。
- 成功只能登记 `【发版】【模拟生产】` 证据任务，不能写 `发布完成`、关闭需求或跳过产品验收。

## 1. 准备发布

```text
/skill yunxiao-release-operations
准备发布：迭代=统一运营管理平台V1.3
```

操作与效果：

1. 唯一解析迭代并冻结其正式`【交付】`快照；通过每条`【交付】`的`ASSOCIATED→需求`关系自动识别需求，需求不必直接关联迭代；自动选入所有非延期且已`测试完成`的需求。
2. 按[release-batch.md](release-batch.md)运行A/B/C/D分类。
3. A类全部进入本次发版；B类（正式延期或尚未测试完成）记录但不阻塞；只有需求/测试状态未完成的C类，或关系/范围冲突的D类才零写入。test部署、QA证据、用例执行和缺陷闭环不再阻断准备发布。
4. 从迭代交付链和A类需求读取可用的测试任务记录、Codeup仓库、真实目标分支和已有生产流水线，并冻结发布环境、负责人、审批、窗口、回滚方案及生产验证计划。
5. 创建或复用唯一顶层`【发版】`任务；它不作为任何【交付】的子任务，而是按迭代正式关联A类需求及其多个源交付/测试任务。
6. 以该迭代读取未关联任何【交付】、已完成或已关闭的Bug，正式关联到发版任务；不得扫描或混入其他迭代/项目的Bug。
7. 在任务描述中写入受管A/B/C/D范围、源交付清单、无交付已完成Bug清单、可读取的测试记录摘要、范围哈希、生产资产和验证计划。
8. 回读发版任务顶层关系、全部正式关联、范围哈希、生产验证计划和幂等键，返回发版任务ID；不以QA证据完整性阻止通过。
9. 不运行生产流水线、不写`发布中`或`发布完成`。

`需求=ONEOS-101,ONEOS-102`仅用于热修复、灰度或明确的局部发布；不提供时即按迭代自动识别范围。已冻结的发版任务不会因为稍后又有需求测试完成而自动扩容；范围变化必须阻塞并显式处理。

下一条：

```text
/skill yunxiao-release-operations
执行发布：发版任务=<发版任务ID>
```

## 2. 执行测试流水线

```text
/skill yunxiao-release-operations
执行测试流水线：流水线=流水线名称
```

操作与效果：

1. 使用显式名称唯一匹配已有测试流水线；生命周期自动节点则按正式范围中的Codeup仓库、代码源和目标分支匹配名称带`test/测试`的已有流水线，并立即启动一次，不二次确认。
2. 返回执行ID、链接、开始时间和初始状态，跟踪到终态。
3. 失败时自动抓取首个失败步骤日志并脱敏分析。
4. 不创建、复制、修改、重命名或删除流水线，也不修改工作项状态。
5. 同名多条、环境不符、参数缺失或权限不足时不执行并说明原因。

## 3. 执行生产流水线

```text
/skill yunxiao-release-operations
执行生产流水线：流水线=流水线名称
```

操作与效果：

1. 使用显式名称唯一匹配已有生产流水线；生命周期自动节点则按正式范围中的Codeup仓库、代码源和目标分支匹配名称带`prod/生产`的已有流水线，并立即启动一次，不二次确认。
2. 返回执行ID、链接、开始时间和初始状态，跟踪到终态。
3. 失败时自动抓取首个失败步骤日志并脱敏分析。
4. 不创建、复制、修改、重命名或删除流水线，不自动写发布状态。
5. 该独立命令没有发版任务、冻结回滚目标和生产验证计划，因此失败时只反馈问题、不自动回滚；需要完整发布闭环时使用`执行发布`。

## 4. 执行发布

```text
/skill yunxiao-release-operations
执行发布：发版任务=TASK-900
```

唯一必填字段：`发版任务`。

`执行发布`只负责首次发布尝试和同一次尝试的接续。首次通过全部门禁、准备提交生产前，写入`attemptNo=1`、`attemptType=initial`和唯一`releaseAttemptId`；中断、监控失败或会话重启后再次输入本命令，只能关联同一尝试、同一生产执行或同一自动回滚，不得创建第二次生产执行。只有尝试进入明确成功或失败终态，才算该次尝试结束。

先读取真实状态，再自动决定：

| 当前状态 | 自动操作 |
|---|---|
| 已准备/待发布，且不存在历史发布尝试 | 校验门禁，创建首次`releaseAttemptId`，启动一次生产流水线并跟踪 |
| 发布中/执行中，且当前尝试未终结 | 按`releaseAttemptId`接续已有生产执行、生产验证或监控；禁止重复启动 |
| 发布失败且回滚未完成 | 自动执行或接续已保存的回滚，禁止重复启动 |
| 发布失败且回滚已成功 | 首次/当前尝试已终结；不重复回滚、不创建生产执行；转入正式修复回流，全部门禁通过后只能使用`重新发布` |
| 发布完成 | 不重跑生产；补做证据、错误关闭检查和跨Skill交接；上线异常需使用`执行回滚` |
| 已完成/已关闭 | 不重跑；只核验是否由产品验收正常关闭 |

生产流水线技术成功后自动执行：

1. 验证prod环境、执行ID、范围、回调和幂等。
2. 固化生产Tag、Commit或不可变制品摘要。
3. 发版任务和需求保持`发布中`，按准备发布时冻结的计划执行健康检查、关键接口/页面、最小业务冒烟和指标观察。
4. 全部必选检查在完整观察窗口内通过后，写入并回读生产验证证据。
5. 只有生产流水线与生产验证均通过，发版任务和需求才进入`发布完成`。
6. 两次检查是否被旧规则错误自动关闭。
7. 输出产品验收交接。

失败后自动执行：

1. 流水线进入明确的不可继续终态，或冻结的生产验证项明确失败时，分别保存流水线日志或验证证据；未知、无权限、观测中断不冒充失败。
2. 保存失败类型、失败执行/验证项、问题现象、影响范围、证据和已配置回滚方案。
3. 发版任务进入`发布失败`。
4. 在同一命令内核验稳定版本锚点、回滚目标、制品、权限和幂等，然后自动执行或接续一次回滚。
5. 跟踪回滚到终态，记录原执行ID、回滚执行ID、回滚前后版本和证据。
6. 回滚成功后发版任务仍保持真实`发布失败`，需求如何处置交产品或项目负责人决定。
7. 回滚失败时保留日志和现场，不自动重试。

每次失败和回滚必须反馈：

```text
问题类型：生产流水线失败 | 生产验证失败 | 主动回滚
问题现象/发生时间：
失败阶段或验证项：
脱敏日志/监控/业务证据：
诊断结论：日志确认原因 | 可能根因 | 仅观察到的现象
影响需求/服务/用户范围：
生产执行ID/上线版本：
回滚是否触发/回滚执行ID：
回滚前后版本/恢复验证：
当前状态/剩余风险：
责任人/下一步：
```

新的消息再次输入同一发版任务：

- 尚未创建发布尝试且仍为`已准备/待发布`时，可创建首次尝试并执行。
- 当前`releaseAttemptId`仍在创建、执行、生产验证、监控中断或回滚阶段时，只接续该尝试，不创建新尝试或新生产执行。
- 当前尝试已成功时，幂等返回发布完成证据，不重复生产。
- 当前尝试已失败时，普通`执行发布`永远不构成生产重试授权；回滚未完成时只接续回滚，回滚完成时只返回失败、回滚和修复回流证据。即使失败原因已经处理并重新审批，也必须输入`重新发布`，由其校验完整修复链并创建下一次尝试。
- 任务为`发布完成`时，只执行收尾，不重复运行生产流水线。

以下不视为失败终态，也不触发回滚：等待流水线内部审批、缺少运行参数、登录/OTP、权限提升、仍在运行、监控不可用、证据缺失、平台状态未知或页面暂时不可读。只有冻结的生产验证计划事先明确把某个可观测条件定义为失败阈值时，命中该条件才触发回滚。

## 5. 执行回滚

```text
/skill yunxiao-release-operations
执行回滚：发版任务=TASK-900 原因=核心业务验证失败 证据=https://example.com/incident
```

三个字段都必填：

- `发版任务`：精确发版任务编号。
- `原因`：可审计的问题现象，不能只写“有问题”。
- `证据`：监控告警、失败探针、业务验证记录或事故记录的ID/URL；聊天转述不能单独作为失败事实。

操作与效果：

1. 唯一读取发版任务、当前生产版本、最近成功生产执行、正式发布范围和产品验收状态。
2. 只处理已经技术部署或处于`发布完成`、但尚未由产品验收关闭的生命周期；`已完成/已关闭`不重开，交回`YunxiaoPM`建立线上缺陷/热修复生命周期。
3. 回读并核验问题证据与本次发布的时间、环境和范围一致；证据不足或范围冲突时零执行。
4. 读取准备发布时冻结的回滚方案、稳定版本锚点、制品、权限和幂等记录，不接受命令临时覆盖目标版本。
5. 先记录线上问题并把发版任务写入项目真实`发布失败`状态；项目不支持该迁移时保留实际状态、写证据并明确报告状态不一致。
6. 自动执行或接续唯一一次回滚，跟踪终态，随后执行恢复健康检查和最小业务验证。
7. 回滚成功后保持`发布失败`，不自动重新发布，不回退需求业务状态；输出问题、影响、回滚及恢复结果。
8. 回滚失败时保存现场和脱敏日志，禁止自动重试，输出人工恢复所需条件。

`执行发布`已因流水线或生产验证失败触发回滚时，不需要再输入本命令；重复输入只接续运行中的回滚或幂等返回成功证据。

## 6. 重新发布

```text
/skill yunxiao-release-operations
重新发布：发版任务=TASK-900 回归证据=<ID或URL>
```

仅用于发布失败或产品验收不通过后的正式修复回流。必须验证原失败/验收证据、回滚或fix-forward处置、QA回流批次、每个Bug的独立复测证据、新test部署、回归证据清单和重新审批；生成新的发布尝试ID后再执行生产与完整验证。不得用重复`执行发布`绕过修复回流。

新尝试必须写入`attemptNo=上一尝试+1`、`attemptType=re_release`、新的`releaseAttemptId`、`previousAttemptId`和新幂等键。若重新发布再次失败，后续仍需完成新一轮修复回流后再次输入`重新发布`创建再下一次尝试；不得退回普通`执行发布`。

## 7. 查询发布

```text
/skill yunxiao-release-operations
查询发布：发版任务=TASK-900
```

唯一必填字段：`发版任务`。不接受`需求=`或`执行ID=`作为查询入口。

操作与效果：

1. 按发版任务ID唯一定位发版任务。
2. 返回项目、迭代、需求范围、当前状态和生产流水线。
3. 返回全部发布尝试的序号、类型、`releaseAttemptId`、前次尝试ID、生产执行ID、生产验证结果、最终状态、问题证据、失败日志和回滚情况。
4. 检查回调重复、幂等、状态未流转及错误自动关闭。
5. 给出当前阻塞和下一条建议口令。
6. 永远只读，不执行流水线，不写状态。

## 跨Skill产品验收

不计入本Skill八条命令。只有`执行发布`或`重新发布`完成生产验证并进入`发布完成`后输出：

```text
/skill YunxiaoPM
验收通过：发版任务=TASK-900；验收人=王经理；证据=https://example.com/acceptance
```

## 合并结果

以下旧口令不再作为独立入口：

- `开始发布`
- `组建发布批次`
- `发布成功`
- `重试发布`
- `主动回滚`
- `分析流水线失败`
- `为什么发布没有流转`
- `查发布范围`
- `查重复回调`
- `查发布完成后是否被自动关闭`

`分析流水线失败`不再是独立口令：测试/生产流水线命令和`执行发布`失败时自动输出失败步骤、验证项、脱敏日志、诊断、影响与建议；历史执行通过其所属发版任务使用`查询发布：发版任务=...`读取。`主动回滚`统一为`执行回滚`。其余旧入口分别合并进`执行发布`或`查询发布`。`发布失败`也不是独立口令；执行中的失败识别、状态回写和自动回滚由同一次`执行发布`完成。

`组建发布批次`已合并进`准备发布：迭代=<名称>`；收到旧口令时只返回替代口令，不创建`【执行】`任务、不写发布范围。

发布或产品验收失败后的固定链路为：`接收发布回流 → 修复bug/处理发布回流 → 验证发布回流 → 重新发布 → 新一轮产品验收`。
