# 开发大脑知识治理

## 记录模型

每条记录包含：

```text
ID：DB-C-000
状态：confirmed | candidate | pending | conflicted | superseded
适用范围：项目/仓库/模块/语言或框架/版本/动作；不可留空
规则或复盘：可执行、可验证的最小表述
证据来源：任务、需求、提交/MR、缺陷、测试或何斐确认的可定位引用
验证：现象、根因、修复或规避、验证结果（候选至少应具备）
记录日期：YYYY-MM-DD
复核触发：版本升级、架构替换、证据冲突或定期复核日期
冲突/过期处理：保留旧记录并说明替代/裁决需求
```

## 状态与写入规则

- `confirmed`：何斐明确确认，或严格满足“两次独立完成的开发任务验证 + 95 分以上 + 全部安全门槛”的约束。可在范围内强制执行。
- `candidate`：当前任务证据支持复用可能性，但尚未达到确认条件。仅供提示，不可强制。
- `pending`：问题、范围或裁决尚缺；不可强制。
- `conflicted`：同范围存在相反的有效证据；暂停引用，列出冲突而不自行裁决。
- `superseded`：被明确的新规则替代；保留以便追溯，不再引用。

新增候选和人工确认的新知识都必须先做相同/近似模式排除：现象、根因、预防动作与适用范围四项中，三项实质重合即视为近似；四项重合即视为相同。命中 `confirmed` 后不新增；命中 `candidate` 后不得创建重复记录，只能追加第二组独立闭环证据或提升原记录。任何升级、降级、冲突或替代必须保留原 ID、时间和依据。

## 冲突优先级

用户本轮明确指令和安全要求优先；其后是当前仓库 `AGENTS.md` 与已确认任务材料；再后是范围匹配的 `confirmed` 记录。发现冲突时，停止受影响实现，输出冲突记录、影响和需何斐确认点。不得用旧经验覆盖当前需求或仓库事实。

## 证据标准

代码现象、日志或一次性口头推断不足以生成 `confirmed`。至少需要能定位的来源，以及与该来源一致的复现/根因/修复或规避/验证证据；范围不清则保留 `candidate`。严禁写入凭据、密钥、Cookie、个人敏感信息或生产数据。

## 通用性准入

记录必须表达稳定的可执行行为，而不是某一次任务的状态。它应能在声明的技术/风险范围内被后续任务复用，且不能依赖某天的工作区、分支、提交、待办状态或文件数量。

- 可入库：有完整证据的根因—规避—验证模式，或何斐确认的长期开发约束。
- 不入库：仓库路径、分支/提交、脏工作区数量、当前依赖版本、构建脚本、平台缺陷列表、单个缺陷现象、临时排障过程和当次验收数字。
- 项目规则以实时 `AGENTS.md`、设计文档、构建配置和 CI 为准；缺陷详情以对应平台实时记录为准。它们可作为本次证据，但不复制进大脑。
- 一条候选若无法去除个案信息后仍保留明确的适用条件、预防动作和验证方式，则不入库；只在当次回执中记录。

## 置信度与自动入库

置信度用于决定候选知识是否值得沉淀，不代表事实绝对正确，也不替代 `confirmed` 的证据标准。

| 维度 | 满分 | 判断要点 |
| --- | ---: | --- |
| 通用性与稳定性 | 35 | 能否跨后续同类任务复用，且不依赖一次性工作区或日期快照 |
| 证据闭环 | 30 | 是否有可定位来源，以及现象、根因、规避/修复、验证的闭环证据 |
| 可执行与可验证性 | 20 | 是否能写成清晰预防动作，并由测试、扫描或回读验证 |
| 边界与冲突 | 15 | 适用/不适用范围是否明确，是否已排除冲突和过期证据 |

硬门槛：不得含凭据、个人/生产敏感数据；不得是项目配置、平台快照或单个问题复述；不得与当前任务材料、仓库规则或已确认约束冲突；不得缺少可定位证据来源。与既有 `confirmed` 相同或近似时不写；与 `candidate` 相同或近似时进入独立证据验证，不新增记录。

- `90–100`：仅在所有硬门槛通过、通用性不少于 30、证据闭环不少于 25、可执行与可验证性不少于 15 时，自动形成新的 `candidate`，并立即按 GitHub 同步门禁推送和读回。
- `70–89`：不自动写入。向何斐展示候选摘要、得分拆解、证据缺口、适用范围，询问是否作为 `candidate` 加入；确认后也必须立即按 GitHub 同步门禁推送和读回。
- `<70`：忽略，不写入；当次回执标明主要不足即可。
- 任一硬门槛失败：无论分数一律忽略；不得用何斐未明确的“特殊批准”推翻凭据/敏感数据和个例快照禁令。
- 命中既有 `candidate` 且本轮达到 `95–100`：仅当任务/缺陷、提交或 MR、验证执行三类证据均与首轮独立，并再次闭环证明同一模式时，自动将原记录提升为 `confirmed`；保留原 ID、两组证据和提升日期。
- 同一任务的重试、续跑、补充、重复构建或同一提交的再次验证不构成第二组独立证据。
- 破坏性操作、权限扩大、绕过安全、生产变更/发布/回滚、强推、敏感凭据处理、降低测试/审计/审批门槛的规则永不自动确认，必须由何斐明确确认。

## GitHub 即时同步

新增 `candidate`、自动验证/提升既有候选，或何斐确认新增/升级知识前，必须完整阅读 [GitHub 同步门禁](github-sync.md) 并先通过其发布预检。GitHub 远端提交与 `main` 分支读回成功，是“已入脑”的必要条件；任何本地草稿、未推送提交或安装目录修改都不算入脑。
