# 历史代码交付恢复

当开发任务晚于实际编码创建，或分支、提交、MR已经存在但任务没有代码关联和交付台账时，使用本流程恢复证据。恢复只补齐真实历史归属，不创建重复提交或MR，也不把同模块的全部代码自动算给当前任务。

## 识别缺口

先通过官方CLI读取开发任务的代码扩展关系、受管评论和交付台账，再读取适用仓库的Codeup分支、提交与MR。分开判断：

- **物理代码不存在**：没有远端分支、提交、MR或集成版本，保持`remoteDelivery=pending`并停止完成开发。
- **物理代码存在但任务未关联**：官方Codeup能读到分支/MR/提交，而开发任务没有对应关系或台账，进入可恢复状态。
- **源分支已删除但MR已合并**：合并MR、源分支名、精确提交、目标分支和`mergedAt`均可官方读回时，不因为源分支已删除判为无代码。
- **只有相似模块记录**：仅作者、模块名或时间范围相似，不能直接认领。

## 冻结候选集合

候选至少同时满足仓库属于当前交付范围、作者或协作者可解释、创建/合并时间落在任务实际开发窗口附近、差异文件与验收范围不冲突。逐条保存：仓库ID与名称、MR编号、源/目标分支、源提交与合并提交、状态、创建和合并时间、标题、文件差异摘要。

把候选分成三组：

1. `initial-delivery`：实现任务主体的提交或MR。
2. `bug-retest`：测试后按Bug修复的提交或MR，保留Bug归属，不混入初始实现。
3. `unresolved`：只能证明模块相似，无法唯一归属当前任务。

任务编号、已有受管台账或正式Codeup关系能唯一证明归属时，可直接恢复。否则展示精确候选集合并只确认一次；禁止用“全部故障代码”“作者最近100条提交”等模糊范围提问。

## 补录与复核

确认后按真实时间顺序追加`EXTERNAL_COMMIT_DISCOVERED`、`MR_RECORDED`、`MR_MERGED`和必要的`DELIVERY_MAPPING_CORRECTED`事件；`occurredAt`保留原始Codeup时间，云效评论时间只表示补录时间。逐仓尝试建立需求和开发任务的代码关系，失败时保留台账证据和错误，不伪造关系成功。

补录后重新官方读回并校验：每个适用仓库有唯一交付版本，所有MR目标都是该仓库已核验集成分支，合并提交包含精确源提交，初始交付与Bug修复没有混算。然后把`remoteDelivery`改为`verified`并重跑完成判断。

缺少或不完整的`oneos.delivery-handoff/v1`记为待产品补齐，不能仅因产品交接格式缺失阻断完成开发或创建测试任务；不得补造产品确认。真实代码版本、开发验证或任务归属缺失仍需恢复。已经存在测试任务时复用原任务并补齐`oneos.test-scope/v1`，不得重复创建；需求已经在`待测试`或`测试中`时保持当前状态，不回退工作流。TestHub计划读取直接使用官方JSON适配器，固定`Content-Type: application/json`；不探测旧CLI或升级重试插件。真实服务/连接失败时按测试范围规则披露错误并跳过该读取阶段，权限等阻断条件与测试任务红线不变。
