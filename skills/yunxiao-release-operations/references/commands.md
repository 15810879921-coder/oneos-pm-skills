# 发布运维七条口令

本文件七条口令中的全部云效 Projex、Flow、Codeup 和 AppStack 读取与写入只通过官方 `aliyun devops` CLI 及 `yunxiao_cli_gateway.py` 执行。浏览器、视觉点选、DOM、Cookie、连接器和网页内部接口均不是执行或回退通道。

## 通用格式

每次先显式启用：

```text
$yunxiao-release-operations
```

下一行输入业务口令。字段之间使用空格，不需要分号。

## 附：受限模拟生产冒烟（仅显式授权时）

当用户明确要求“从既有测试流水线复制一个副本，在测试环境模拟生产”时，先执行受限设置动作，再运行副本；如果 CLI 无法解析源流水线已用的构建组，则不创建副本，改为把既有测试流水线运行一次，并将结果标记为 `releaseMode=smoke`。

- 仅允许源流水线为日常环境、名称含 `test`；副本名称必须同时含 `smoke` 和 `prod`，且绝不能是实际 `prod` 流水线。
- 不创建 Runner、主机组、服务连接、容器、部署目标或 Webhook；移除通知插件；仅手工触发。
- 成功只能登记 `【发版】【模拟生产】` 证据任务，不能写 `发布完成`、关闭需求或跳过产品验收。

## 1. 准备发布

```text
$yunxiao-release-operations
准备发布：迭代=统一运营管理平台V1.3
```

操作与效果：

1. 唯一解析迭代并冻结其正式`【交付】`快照；通过每条`【交付】`的`ASSOCIATED→需求`关系自动识别需求，需求不必直接关联迭代；自动选入所有非延期且已`测试完成`的需求。
2. 读取源【交付】端侧标签，判定本迭代端别为`Web`或`小程序`；`PC`视为`Web`。混端或无法判定时零写入。
3. 按[release-batch.md](release-batch.md)运行A/B/C/D分类。
4. A类全部进入本次发版；B类（正式延期或尚未测试完成）记录但不阻塞；只有需求/测试状态未完成的C类，或关系/范围冲突的D类才零写入。test部署、QA证据、用例执行和缺陷闭环不再阻断准备发布。
5. **Web**：从交付链冻结唯一活动生产流水线；同时读取本批任务/缺陷已有`【代码交付记录】`评论，收集其中可用的仓库、源/目标分支、提交、MR和可选流水线信息。评论只能辅助汇总，不能替代正式范围、Codeup或Flow实时事实。**小程序**：不要求、不冻结云效生产流水线；发版任务注明`releaseChannel=miniprogram_skip_pipeline`。
6. 创建或复用唯一顶层`【发版】`任务；它不作为任何【交付】的子任务，而是按迭代正式关联A类需求及其多个源交付/测试任务。
7. 以该迭代读取没有任何正式关联单据、已完成或已关闭的Bug，正式关联到发版任务；不得扫描或混入其他迭代/项目的Bug。
8. 自动读取本批A类需求和纳入Bug的标题、完整描述、验收标准、模块、标签、类型和角色信息，按[release-description.md](release-description.md)生成业务更新日志：顶部只显示版本更新日志，按`【新功能】/【Bug修复】`分组并连续编号；另外在【发版】任务评论中写入`【发布代码清单】`，逐项记录已有仓库、待合并分支、提交、MR及可唯一定位的流水线。关系、范围哈希、幂等键和更新日志源ID映射写入正文末尾的隐藏HTML注释。
9. 回读并校验更新日志标题、分组、连续编号和范围覆盖，再回读顶层关系、全部正式关联、范围哈希、端别、`【发布代码清单】`评论、Web生产流水线或小程序跳过标记，以及幂等键，返回发版任务ID；可选流水线信息缺失不阻止准备通过。
10. 不运行生产流水线、不写`发布中`或`发布完成`。

`需求=ONEOS-101,ONEOS-102`仅用于热修复、灰度或明确的局部发布；不提供时即按迭代自动识别范围。已冻结的发版任务不会因为稍后又有需求测试完成而自动扩容；范围变化必须阻塞并显式处理。

重复执行相同迭代、相同范围时，必须复用已有发版任务，重新读取迭代内容并重生成业务更新日志，只修正描述与本Skill受管注释，不创建新任务、不改变正式关系、不启动生产。

下一条：

```text
$yunxiao-release-operations
执行发布：发版任务=<发版任务ID>
```

## 2. 执行测试流水线

```text
$yunxiao-release-operations
执行测试流水线：流水线=流水线名称
```

操作与效果：

1. 使用显式名称唯一匹配已有测试流水线；生命周期自动节点则按正式范围中的Codeup仓库、代码源和目标分支匹配名称带`test/测试`的已有流水线，并立即启动一次，不二次确认。
2. 返回执行ID、链接、开始时间和初始状态，跟踪到终态。
3. 失败时自动抓取首个失败步骤日志并脱敏分析。
4. 不创建、复制、修改、重命名或删除流水线，也不修改工作项状态。
5. 同名多条、环境不符、参数缺失或权限不足时不执行并说明原因。

## 3. 执行生产流水线

```text
$yunxiao-release-operations
执行生产流水线：流水线=流水线名称
```

操作与效果：

1. 使用显式名称唯一匹配已有生产流水线；生命周期自动节点则按正式范围中的Codeup仓库、代码源和目标分支匹配名称带`prod/生产`的活动流水线，先忽略`*-old`等退役定义，再立即启动一次，不二次确认。Flow原始`envName=日常环境`不单独否定生产语义。
2. 返回执行ID、链接、开始时间和初始状态，跟踪到终态。
3. 失败时自动抓取首个失败步骤日志并脱敏分析。
4. 不创建、复制、修改、重命名或删除流水线，不自动写发布状态。
5. 该独立命令没有发版任务、冻结回滚目标和生产验证计划，因此失败时只反馈问题、不自动回滚；需要完整发布闭环时使用`执行发布`。

## 4. 执行发布

```text
$yunxiao-release-operations
执行发布：发版任务=TASK-900
```

唯一必填字段：`发版任务`。口令格式不变。

先读取并复核冻结的`【发布代码清单】`，再回读发版任务关联的源【交付】端侧标签（`Web` / `小程序`）。只核验清单中的仓库、分支、提交、MR、流水线和目标环境是否仍一致；不再对整个迭代重新搜寻代码范围。任一清单项漂移时停止并要求重新`准备发布`，再分流（混端或无法判定则停）：

| 端别 | `执行发布` 做什么 |
|---|---|
| **Web** | 走下方原有生产流水线 + 生产验证 + 成败回写逻辑（不变） |
| **小程序** | **不跑**云效生产流水线；**不要求**外部平台证据；默认本批已发布，直接把发版任务与本批需求写入`发布完成`，再做错误关闭检查并输出产品验收交接 |

### 小程序捷径（产品确认）

1. 校验发版任务顶层关系、冻结范围与源交付均为`小程序`标签。
2. 写入并回读一次受管发布尝试：`attemptType=miniprogram_skip_pipeline`，`productionExecutionId=null`，`status=成功`；备注「小程序跳过流水线，默认发布完成」。
3. 发版任务、本批需求 → `发布完成`。
4. 不做生产验证、不触发自动回滚。
5. 输出 `$YunxiaoPM` 产品验收交接（与 Web 成功后的后续相同）。
6. 重复执行同一发版任务且已`发布完成`时幂等返回，不重复改状态。

### Web（原逻辑，不变）

`执行发布`只负责首次发布尝试和同一次尝试的接续。首次通过全部门禁、准备提交生产前，写入`attemptNo=1`、`attemptType=initial`和唯一`releaseAttemptId`；中断、监控失败或会话重启后再次输入本命令，只能关联同一尝试、同一生产执行或同一自动回滚，不得创建第二次生产执行。只有尝试进入明确成功或失败终态，才算该次尝试结束。

先读取真实状态，再自动决定：

| 当前状态 | 自动操作 |
|---|---|
| 已准备/待发布，且不存在历史发布尝试 | 校验门禁，创建首次`releaseAttemptId`，启动一次生产流水线并跟踪 |
| 发布中/执行中，且当前尝试未终结 | 按`releaseAttemptId`接续已有生产执行、生产验证或监控；禁止重复启动 |
| 发布失败且回滚未完成 | 自动执行或接续已保存的回滚，禁止重复启动 |
| 发布失败且回滚已成功 | 首次/当前尝试已终结；不重复回滚、不创建生产执行；转入正式修复回流，全部门禁通过后只能使用`重新发布` |
| 发布完成 | 不重跑生产；补做证据、错误关闭检查和跨Skill交接；上线异常需使用`执行回滚` |
| 已完成/已关闭 | 不重跑；只核验是否由产品验收正常关闭 |

生产流水线技术成功后自动执行：

1. 验证逻辑prod环境、唯一执行ID、冻结范围和幂等。
2. 记录可读取的生产Tag、Commit或制品摘要；读取不到时标记`未获取`，不阻断。
3. 执行当前可用的健康检查、关键接口/页面、业务冒烟或指标观察；没有自动化入口时标记`未自动验证`，不伪造结果。
4. 生产流水线终态成功且环境、范围回读一致后，写入并回读技术发布证据。
5. 发版任务和本批需求进入`发布完成`；可选生产检查的缺失只形成风险提示，不阻断技术发布完成。
6. 两次检查是否被旧规则错误自动关闭。
7. 输出产品验收交接，由产品/业务验收承担最终业务确认。

失败后自动执行：

1. 流水线进入明确的不可继续终态，或实际执行的生产检查明确失败时，分别保存流水线日志或验证证据；未知、无权限、观测中断不冒充失败。
2. 保存失败类型、失败执行/检查项、问题现象、影响范围、证据和可读取的回滚信息。
3. 发版任务进入`发布失败`。
4. 只有稳定版本锚点、回滚目标、制品、权限和幂等均可验证时，才自动执行或接续一次回滚。
5. 回滚条件不完整时不猜测，返回`自动回滚=false`和人工恢复边界；这不反向否定此前用户对生产执行的授权。
6. 已触发回滚时跟踪到终态，记录原执行ID、回滚执行ID、回滚前后版本和证据。
7. 回滚成功后发版任务仍保持真实`发布失败`；回滚失败时保留日志和现场，不自动重试。

每次失败和回滚必须反馈：

```text
问题类型：生产流水线失败 | 生产验证失败 | 主动回滚
问题现象/发生时间：
失败阶段或验证项：
脱敏日志/监控/业务证据：
诊断结论：日志确认原因 | 可能根因 | 仅观察到的现象
影响需求/服务/用户范围：
生产执行ID/上线版本：
回滚是否触发/回滚执行ID：
回滚前后版本/恢复验证：
当前状态/剩余风险：
责任人/下一步：
```

新的消息再次输入同一发版任务：

- 尚未创建发布尝试且仍为`已准备/待发布`时，可创建首次尝试并执行。
- 当前`releaseAttemptId`仍在创建、执行、生产验证、监控中断或回滚阶段时，只接续该尝试，不创建新尝试或新生产执行。
- 当前尝试已成功时，幂等返回发布完成证据，不重复生产。
- 当前尝试已失败时，普通`执行发布`永远不构成生产重试授权；回滚未完成时只接续回滚，回滚完成时只返回失败、回滚和修复回流证据。即使失败原因已经处理并重新审批，也必须输入`重新发布`，由其校验完整修复链并创建下一次尝试。
- 任务为`发布完成`时，只执行收尾，不重复运行生产流水线。

以下不视为失败终态，也不触发回滚：等待流水线内部审批、缺少运行参数、登录/OTP、权限提升、仍在运行、监控不可用、可选证据缺失、平台状态未知或页面暂时不可读。只有流水线明确失败，或实际执行的生产检查得到明确失败结果时，才进入失败分支。

## 5. 执行回滚

```text
$yunxiao-release-operations
执行回滚：发版任务=TASK-900 原因=核心业务验证失败 证据=https://example.com/incident
```

三个字段都必填：

- `发版任务`：精确发版任务编号。
- `原因`：可审计的问题现象，不能只写“有问题”。
- `证据`：监控告警、失败探针、业务验证记录或事故记录的ID/URL；聊天转述不能单独作为失败事实。

操作与效果：

1. 唯一读取发版任务、当前生产版本、最近成功生产执行、正式发布范围和产品验收状态。
2. 只处理已经技术部署或处于`发布完成`、但尚未由产品验收关闭的生命周期；`已完成/已关闭`不重开，交回`YunxiaoPM`建立线上缺陷/热修复生命周期。
3. 回读并核验问题证据与本次发布的时间、环境和范围一致；证据不足或范围冲突时零执行。
4. 读取准备发布时冻结的回滚方案、稳定版本锚点、制品、权限和幂等记录，不接受命令临时覆盖目标版本。
5. 先记录线上问题并把发版任务写入项目真实`发布失败`状态；项目不支持该迁移时保留实际状态、写证据并明确报告状态不一致。
6. 自动执行或接续唯一一次回滚，跟踪终态，随后执行恢复健康检查和最小业务验证。
7. 回滚成功后保持`发布失败`，不自动重新发布，不回退需求业务状态；输出问题、影响、回滚及恢复结果。
8. 回滚失败时保存现场和脱敏日志，禁止自动重试，输出人工恢复所需条件。

`执行发布`已因流水线或生产验证失败触发回滚时，不需要再输入本命令；重复输入只接续运行中的回滚或幂等返回成功证据。

## 6. 重新发布

```text
$yunxiao-release-operations
重新发布：发版任务=TASK-900 回归证据=<ID或URL>
```

仅用于发布失败或产品验收不通过后的正式修复回流。必须验证原失败/验收证据、原范围不变、受影响Bug已关闭、当前回归证据和本次显式重发授权；QA回流批次、新test部署、逐Bug结构化复测、回滚/fix-forward、审批和窗口有则记录，缺少自定义结构化格式不阻断。生成新的发布尝试ID后再执行生产，不得用重复`执行发布`绕过修复回流。

新尝试必须写入`attemptNo=上一尝试+1`、`attemptType=re_release`、新的`releaseAttemptId`、`previousAttemptId`和新幂等键。若重新发布再次失败，后续仍需完成新一轮修复回流后再次输入`重新发布`创建再下一次尝试；不得退回普通`执行发布`。

## 7. 查询发布

```text
$yunxiao-release-operations
查询发布：发版任务=TASK-900
```

唯一必填字段：`发版任务`。不接受`需求=`或`执行ID=`作为查询入口。

操作与效果：

1. 按发版任务ID唯一定位发版任务。
2. 返回项目、迭代、需求范围、当前状态和生产流水线。
3. 返回全部发布尝试的序号、类型、`releaseAttemptId`、前次尝试ID、生产执行ID、生产验证结果、最终状态、问题证据、失败日志和回滚情况。
4. 检查回调重复、幂等、状态未流转及错误自动关闭。
5. 给出当前阻塞和下一条建议口令。
6. 永远只读，不执行流水线，不写状态。

## 跨Skill产品验收

不计入本Skill七条命令。只有`执行发布`或`重新发布`在生产流水线成功且环境、范围回读一致并进入`发布完成`后输出：

```text
$YunxiaoPM
验收通过：发版任务=TASK-900；验收人=王经理；证据=https://example.com/acceptance
```

## 合并结果

以下旧口令不再作为独立入口：

- `开始发布`
- `组建发布批次`
- `发布成功`
- `重试发布`
- `主动回滚`
- `分析流水线失败`
- `为什么发布没有流转`
- `查发布范围`
- `查重复回调`
- `查发布完成后是否被自动关闭`

`分析流水线失败`不再是独立口令：测试/生产流水线命令和`执行发布`失败时自动输出失败步骤、验证项、脱敏日志、诊断、影响与建议；历史执行通过其所属发版任务使用`查询发布：发版任务=...`读取。`主动回滚`统一为`执行回滚`。其余旧入口分别合并进`执行发布`或`查询发布`。`发布失败`也不是独立口令；执行中的失败识别、状态回写和自动回滚由同一次`执行发布`完成。

`组建发布批次`已合并进`准备发布：迭代=<名称>`；收到旧口令时只返回替代口令，不创建`【执行】`任务、不写发布范围。

发布或产品验收失败后的固定链路为：`接收发布回流 → 修复bug/处理发布回流 → 验证发布回流 → 重新发布 → 新一轮产品验收`。
