# 分配任务的技术实施方案

分配任务不再直接从一段需求描述生成方案。先按[开发需求快照](requirement-snapshot.md)读取关联需求及权威产品材料，固化任务级快照，再由执行 Agent 基于该快照生成方案文件。两个文件一起进入带哈希预检，并依次写入开发任务。

## 必填结构

```markdown
# 技术实施方案：<需求编号> <需求标题>

- 开发需求快照 SHA-256：<64位哈希>

## 实现范围
<本开发任务实现什么、不实现什么、涉及哪个端；必须与快照一致>

## 处理逻辑
<页面、接口、字段、状态、异常和兼容策略；未知事实明确待代码侧核实>

## 实施步骤
1. <按依赖顺序执行的步骤>

## 验证标准
- <与快照验收条件逐条对应的开发侧验证>
```

## 约束

- 必须包含正式关联需求编号和开发需求快照 SHA-256；缺任一项拒绝写入。
- 方案范围、规则与验收只能来自快照；不能用方案反向补造快照。
- 必须覆盖`实现范围`、`处理逻辑`、`实施步骤`和`验证标准`，长度至少 160 字。
- 不得包含`$skill-name`、`开始开发`、`完成开发`等下一步选择器或执行口令。
- 不得猜测仓库路径、具体文件、接口字段或数据表；无法由材料证明的内容写“开工后根据代码事实确认”。
- 方案文件在预检中记录绝对路径和内容哈希；预检后快照或方案任一变化都必须重新预检。

## 开始开发时的使用顺序

1. 先校验开发需求快照的正式需求编号、来源指针及版本。
2. 来源未变化：只精读本任务章节、页面和交互状态；不重读整套原型和完整 PRD。
3. PM 产品快照变化：重新裁剪任务快照，然后重生成绑定新哈希的方案；历史补录材料变化时按同样方式刷新并保留补录标记。
4. 快照未变但方案漏项：只补方案并重新预检/回读，再开始开发。
5. 历史任务缺快照或方案：按只读链路补生成并报告兼容恢复；只有验收关键内容仍不清楚时才阻断受影响范围。

快照和方案都只是实现顺序与追溯输入，不能替代材料、代码、运行环境、验证、提交、MR或云效回读证据。
