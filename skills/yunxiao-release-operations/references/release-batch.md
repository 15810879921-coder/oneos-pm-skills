# 准备发布的范围冻结与A/B/C/D

## 入口

```text
$yunxiao-release-operations
准备发布：迭代=<精确名称>
准备发布：需求=<精确ID,...> 原因=<热修复|灰度|局部发布说明>
准备发布：交付=<精确ID,...> 原因=<热修复|灰度|局部发布说明>
```

标准入口从迭代反查项目，不接受手工项目覆盖。迭代只正式挂载`【交付】`：需求不需要直接关联迭代；只要`【交付】`正式属于该迭代且`ASSOCIATED→需求`有效，即视为该迭代正式需求。例外入口从精确需求或交付ID及正式关系反查唯一项目和范围，必须提供原因，不要求迭代；ID非空、无重复且关系方向唯一。任何跨项目、身份歧义或来源归属冲突均零写入。

## 分类

先冻结迭代全部正式需求快照，再运行：

```powershell
skill-run classify_release_scope.py --input scope.json
```

分类含义：

- A：选入需求状态=`测试完成`且适用测试模式通过。`formal-plan`/`qa-requested-exception`要求精确范围【测试】=`已完成`，存在必需用例时用例=`passed`；`lightweight-verification`要求开发轻量验证=`passed`且存在可信交付版本，不要求【测试】任务。标准入口需经本迭代交付反查，例外入口需经精确源关系反查。进入发布范围。
- B：属于迭代但已正式延期，或默认自动范围下尚未达到`测试完成`的需求。记录为下一批候选，不阻塞本批。
- C：仅局部发布时显式选入但需求或关联【测试】尚未完成的需求。阻塞本批。
- D：跨项目/跨迭代、迭代交付到需求的正式关联缺失、同一需求同时选入和延期、编号不存在或范围冲突。阻塞本批。

测试部署和辅助QA材料只作可选记录；但适用测试模式、存在的必需用例以及活动缺陷属于发布就绪门禁：正式/QA例外测试任务必须完成，已有必需用例必须通过，当前范围活动Bug必须为零；轻量模式则以通过的轻量验证和可信交付版本为准，不补造测试任务。

项目不一致、来源身份不唯一或关系归属冲突归D类且零写入；需求或适用测试模式未完成归C类。对象、项目和来源均唯一时，其他C/D业务缺口允许保存`准备不通过`草稿，但禁止`执行发布`。

只有`A非空 && C为空 && D为空`时才允许写云效。

## 创建顶层【发版】任务并冻结范围

通过后：

1. 以命令中的精确迭代为唯一关系起点：读取该迭代已挂载的全部源`【交付】`，通过每条交付的`ASSOCIATED→需求`关系确定本批需求；B类或其他范围的交付只记录，不关联到本次发版。读取同一迭代的Bug（以Bug迭代字段或可验证的正式关系链为准）；仅当Bug真实状态为`已完成`或`已关闭`且不存在任何正式关联单据（任何关系类型、任何工作项）时，才列为“无关联单据已完成Bug”。不得扫描或混入其他迭代/项目的Bug。
2. 在迭代内按`项目ID + 迭代ID + 排序后的A类需求ID + 排序后的无关联单据已完成BugID + release_prepare`生成幂等键和范围哈希。
3. 创建或复用唯一顶层`【发版】<范围摘要>`任务；它的层级必须高于【交付】，不得以`TASK_SUB`挂到任何【交付】下。本Skill不得填写或改变`sprint/迭代`字段；历史任务已有该字段时原样保留并记录，不作为项目和冻结范围一致时的阻塞项。
4. 发版任务的直接正式关联仅限从标准迭代或例外来源及A类范围派生的多个源【交付】任务，以及同一冻结范围内无关联单据已完成Bug。标准迭代或例外来源、A类需求和已完成【测试】任务仅用于范围与门禁校验，必须写入`【发布受管数据】`评论账本，绝不直接关联到发版任务。一个发版任务可关联多个交付任务，交付任务不成为发版任务的父节点。
5. 读取本批A类需求和纳入Bug的标题、完整描述、验收标准、模块、标签、类型与角色信息，按[release-description.md](release-description.md)自动生成业务更新日志；描述只保留业务正文，使用原生 Markdown 真实换行，禁止 HTML 注释和技术 JSON。把每条日志的源工作项ID、A/B/C/D快照、测试记录摘要、源交付/Bug清单、生成时间、范围哈希、端别和幂等键写入独立的`【发布受管数据】`评论；保留其他人工内容。
6. 同时按**每条源交付及纳入Bug**的端别冻结发布资产：`Web`必须按“仓库 + 已验证生产目标分支 + 部署目标”生成完整组件矩阵；每行包含来源事项、仓库、源/目标分支、目标分支官方验证标记、提交或MR、组件标识、唯一生产流水线ID、流水线代码源/分支/部署目标和逻辑环境。流水线的仓库、目标分支、部署目标和逻辑prod环境必须逐项与代码锚点一致，名称只作提示。事项没有`【代码交付记录】`时，先完成 Codeup 反查并检查精确提交变更树。命中提交所在分支混入范围外提交时只以精确提交建立干净候选MR，不得整支合并。冻结前范围变化必须重建整个矩阵。任一来源事项、生产目标分支或流水线映射无法唯一验证时，Web保持`准备不通过`并列为缺口，禁止执行。`小程序`记录跳过渠道。审批、窗口、回滚方案和生产验证计划可写`未配置`；缺少回滚配置时仅关闭自动回滚。
7. 对所有 Web 源交付和纳入Bug生成`releaseCodeItems`、`codeAnchors`和组件矩阵，运行`skill-run validate_release_component_matrix.py --input <matrix.json>`；只有事项、锚点、变更仓库/组件、`sourceItemIds`和逻辑`prod`流水线全覆盖且结果为`passed`时才可冻结。随后回读发版任务顶层关系，只允许源交付与无关联单据已完成Bug；再从最新有效`【发布受管数据】`评论回读项目、迭代、端别、A类需求、测试任务和范围校验结果，以及Web完整组件矩阵（逐行代码锚点、流水线和逻辑环境）和逐小程序跳过标记与`codeTrace=external_unmanaged`。B类仅记录，不建立本批发布关系；不把测试证据完整性、云效可观测性或待补发布配置作为小程序准备回读阻断条件。
8. 复用发版任务时，必须回读顶层关系和全部受管关联；相同范围时重新读取标准迭代或例外来源内容并自动重生成业务更新日志，描述只替换业务正文。受管载荷相同则复用最新评论，载荷变化则追加新评论并指向前一评论。既有`sprint/迭代`字段原样保留，不写、不清、不作为范围一致时的阻塞。若尚无任何生产尝试，可补齐缺失的应有关联后回读；已有生产尝试时仍可修正文案但不得修改范围或关系；存在`TASK_SUB→【交付】`父子关系、范围/关联冲突或任务不唯一时阻塞，不重挂或扩容历史任务。
9. 范围已冻结的发版任务不得因后来新增的测试完成需求或新关闭Bug自动扩容；范围不一致时阻塞并说明差异。
10. 返回`发版任务ID`，下一条固定为：

```text
$yunxiao-release-operations
执行发布：发版任务=<发版任务ID>
```

重复命令必须复用同一任务；存在多条相同幂等键任务时阻塞，不自动选最新。
