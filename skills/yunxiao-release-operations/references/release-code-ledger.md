# 发布代码清单补录

## 目标

`准备发布`必须为本批每个 A 类需求及纳入 Bug 取得可追溯的远端代码锚点。优先复用事项评论中的 `【代码交付记录】`；评论缺失或字段不完整时，主动通过正式关系和官方 Codeup CLI 反查并补录，不要求开发人员手工回填。

## 每个事项的处理顺序

1. 读取该事项全部 `【代码交付记录】` 评论；只接受可唯一对应的仓库、源分支、目标分支、提交ID或 MR。
2. 评论完整时，实时回读 Codeup 仓库、分支、MR、提交和合并状态，确认评论没有过期。
3. 评论缺失或不完整时，沿事项的正式代码资产、需求/开发任务/交付关系和已关联 MR/分支反查；再用官方 Codeup CLI 读取远端分支、MR 和提交。标题相似、分支名称猜测或纯语义匹配不得单独建立关联。
4. 仅当仓库、源分支、目标分支以及至少一个提交ID或 MR 可唯一验证时，创建并回读一条补录 `【代码交付记录】` 评论：

```text
仓库：<名称或URL>
源分支：<分支>
合并目标：<目标分支>
提交ID：<SHA，多个用逗号分隔>
MR：<编号/URL/当前状态>
需合并分支：<源分支> → <目标分支>
采集方式：准备发布补录
核验时间：<Asia/Shanghai 精确时间>
```

测试/生产流水线字段仍是可选信息：能唯一定位时补充，不能定位时省略，不写“未配置”。

5. 零候选、多候选、跨项目、分支已删除且无可验证MR/提交、或评论与远端事实冲突时，不得补录为成功。记录 `【代码交付核验失败】` 评论（事实、候选、原因、时间），并将该事项列为发布代码清单阻塞项。

## 发布清单与执行

准备发布只在每个选入事项都有已回读的代码交付记录后，创建/更新 `【发版】`任务的 `【发布代码清单】` 评论。清单逐项保留来源事项、仓库、源/目标分支、提交、MR、合并状态及可选流水线。

执行发布只消费这份冻结清单并做最小实时复核；它不再全量重找分支或提交。任一锚点漂移、缺失或仍存在代码核验失败项时，停止执行并要求重新`准备发布`。
