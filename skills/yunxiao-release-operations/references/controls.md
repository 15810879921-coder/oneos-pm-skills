# 发布运维控制

本文件涉及的工作项、关系、流水线、AppStack、执行、日志、状态、发布和回滚操作均只通过官方 `aliyun devops` CLI 与本 Skill 自带适配器执行。任何“接口、自动化、执行、回读”都不包含浏览器、视觉、DOM、Cookie、连接器或网页内部接口。

## 1. 证据边界

发布准备、执行、回滚、重发和查询的流水线发现范围固定为生产环境；测试流水线不读取、不返回、不作为任何生产门禁或映射依据。测试流水线仅允许在独立`执行测试流水线`命令中按显式名称读取。

分别保存，禁止互相替代：

1. test环境部署成功。
2. 测试用例与缺陷闭环完成。
3. 生产流水线执行成功或失败。
4. 生产健康、关键接口/页面、业务冒烟和指标观察结果。
5. 云效关联发布变更完成。
6. 产品/业务验收完成。

本Skill拥有发布准备、`发布中`、`发布完成`和`发布失败`。最终`已完成/已关闭`由产品Skill处理。

### 端侧分流（产品确认）

口令格式不变。按发版范围源【交付】标签分流：

| 标签 | 准备发布 | 执行发布 |
|---|---|---|
| `Web` | 冻结云效生产流水线（原逻辑） | 跑流水线 + 生产验证（原逻辑） |
| `小程序` | 不冻结生产流水线 | **跳过**流水线与外部证据，直接`发布完成`，再交接产品验收 |

混端或无端标签 → 阻塞。`PC` 视为 `Web` 别名。

### 发布尝试账本

发版任务的状态不能单独判断是否允许再次生产。每次生产尝试都必须持久化并回读`oneos.release-attempt/v1`：

```json
{"schemaVersion":"oneos.release-attempt/v1","releaseTaskId":"TASK-900","attemptNo":1,"attemptType":"initial|re_release","releaseAttemptId":"ATTEMPT-1","previousAttemptId":null,"authorizedCommand":"执行发布|重新发布","productionExecutionId":"EXEC-1-or-null","status":"已创建|执行中|生产验证中|成功|失败","idempotencyKey":"release-attempt-..."}
```

在发版任务描述中维护唯一、追加式账本区块；更新当前尝试时保留全部历史尝试，禁止覆盖、删除或重排尝试号：

```html
<!-- YUNXIAO_RELEASE_ATTEMPTS_START -->
<pre>{"schemaVersion":"oneos.release-attempt-ledger/v1","releaseTaskId":"TASK-900","attempts":[{"attemptNo":1,"attemptType":"initial","releaseAttemptId":"ATTEMPT-1","previousAttemptId":null,"authorizedCommand":"执行发布","productionExecutionId":"EXEC-1","status":"失败","idempotencyKey":"release-attempt-1"}]}</pre>
<!-- YUNXIAO_RELEASE_ATTEMPTS_END -->
```

- 首次`执行发布`在全部门禁通过、生产提交前创建`attemptNo=1`、`attemptType=initial`。同一命令重入只能接续该尝试；记录已创建但执行ID为空时，必须先以幂等键核验平台未提交，才能补做唯一一次提交。
- 监控中断、页面不可读、权限暂时受阻、生产仍运行或验证未完成都不终结尝试；恢复后仍用`执行发布`接续同一`releaseAttemptId`。
- 生产执行或冻结生产验证明确失败后，该尝试永久终结为`失败`。普通`执行发布`只能接续/返回其自动回滚和修复交接，不能清空、覆盖或新建生产执行。
- `重新发布`是失败后的唯一新尝试入口。完整修复门禁通过后创建`attemptNo=上一尝试+1`、`attemptType=re_release`、新的`releaseAttemptId`和指向上一尝试的`previousAttemptId`；每次再次失败都重复同一规则。
- 独立`执行生产流水线`不创建发布尝试，不得挂接成发版任务的首次或重发证据，也不得绕过上述命令边界。

## 2. stage_tasks控制

| ID | 事件 | 必要条件 | 动作 | 方式 |
|---|---|---|---|---|
| R11 | 生产执行成功 | 需求=测试完成；冻结生产流水线、目标环境、范围、生产执行和幂等回读有效 | →真实发布完成状态 | 原生/桥接 |
| L01 | 发布完成+全部任务完成→终态 | 会绕过产品验收 | 默认停用 |
| L02 | 测试完成→发布完成后立即终态 | 会形成瞬时状态 | 默认停用 |

进入发布完成后观察两个时点：刚进入时，以及等待5–30秒后。若自动进入终态，记录真实后继规则并判定`误触发`。

## 3. oneos_delivery控制

| ID | 控制 | 运维门禁 |
|---|---|---|
| Y11 | 主任务/需求进入发布中 | 发版任务、迭代、需求范围与唯一生产流水线有效 |
| Y12 | 主任务/需求进入发布完成 | Web：冻结生产流水线成功，且逻辑prod环境、冻结范围与执行ID回读一致；小程序：执行发布捷径校验通过（跳过流水线，默认发布完成） |
| Y13 | 主任务/需求进入发布失败 | 生产失败证据有效并保存原因 |
| Y33 | 提交发版任务 | 顶层`【发版】`按精确迭代正式关联本批需求及其多个源【交付】，并关联同迭代无关联单据且已完成/已关闭的Bug |
| Y34 | 生产发布成功 | 逻辑环境、执行ID、范围、终态成功和幂等均有效；仅实际使用回调时校验签名/时间戳 |
| Y35 | 生产发布失败 | 流水线失败或生产验证失败证据有效，保存原因和影响范围 |
| A08 | 准备发布、创建发版任务和更新说明 | 迭代名称唯一；A/B/C/D分类范围唯一；顶层关系唯一；源交付与无关联单据已完成Bug派生范围唯一；查重、幂等 |
| A09 | 发布成败回写、问题反馈与可选自动/主动回滚 | 防重放、失败重试、审计日志；仅配置自动回滚时要求稳定版本锚点和回滚幂等 |

`执行发布`发现生产执行进入不可继续终态，或实际执行的生产检查明确失败后，先把当前`releaseAttemptId`终结为失败并保存问题和影响证据；仅在回滚配置完整时自动执行一次回滚。`执行发布`不得把`发布失败`重新推进到`发布中`；原范围不变、受影响Bug已关闭、当前回归证据存在且用户明确输入`重新发布`后，才能递增`attemptNo`并创建新的生产尝试，而且必须保留原失败、验证和回滚执行。

## 4. 环境与范围

每个项目分别记录：

- test流水线和执行ID
- prod流水线和执行ID
- 发布变更
- 生产验证计划、检查结果和观察窗口
- 发布任务与迭代
- 本批需求
- 回滚方案
- 产品验收证据

同一执行ID重复回调不得再次推进。回调失败保留失败日志并可安全重试，不能伪造成功。

### 准备发布中的A/B/C/D范围冻结

规范入口：

```text
$yunxiao-release-operations
准备发布：迭代=<精确名称>
```

必须冻结迭代全部正式`【交付】`及其`ASSOCIATED→需求`快照，并用`scripts/classify_release_scope.py`分类：需求无需直接挂迭代；默认自动选入非延期且状态为`测试完成`的需求；仅热修复、灰度或明确局部发布时允许附加`需求=<REQ-ID,...>`覆盖集合。

- A：选入、状态测试完成且可由本迭代交付正式关联唯一反查，进入本批。
- B：迭代内未选入/正式延期，记录但不阻塞、不进入本批。
- C：选入但需求或关联测试任务未完成，阻塞。
- D：跨项目/跨迭代/迭代交付到需求的正式关系缺失或冲突/编号不存在，阻塞。

只有A非空且C/D为空时，才创建或复用唯一顶层`【发版】`任务，并在其中冻结范围。发版任务以迭代为起点，通过正式关联一对多覆盖A类范围的源【交付】，同时关联同迭代无关联单据已完成/已关闭Bug；它不得成为【交付】的`TASK_SUB`子项。完整契约见[release-batch.md](release-batch.md)。

### 准备发布单锚点

规范入口：

```text
$yunxiao-release-operations
准备发布：迭代=统一运营管理平台V1.3
```

处理规则：

1. 按完整名称唯一解析迭代，并以其项目为唯一范围边界。
2. 冻结迭代全部正式`【交付】`及其`ASSOCIATED→需求`快照，自动选入非延期且`测试完成`的A类候选；局部发布时才接受明确`需求=<ID,...>`。
3. 从迭代交付、`TASK_SUB`、`ASSOCIATED`及项目支持的正式关系反查源交付、A类产品需求和测试任务状态；测试计划、结果、部署和缺陷记录只作可选摘要。
4. 发布范围只能取本次分类冻结的A类需求。B类仍记录为延期且不阻塞；出现C/D类、零个A类、范围冲突、无法解释的交付树或混入其他迭代时停止。
5. 从迭代所属项目的生效配置读取prod流水线；先排除禁用、归档及名称带`-old/_old/-legacy/_legacy/旧/停用/废弃/归档`的退役定义，再按代码源、目标分支和部署目标唯一冻结活动流水线。`oneos-web-prod-old`不参与`oneos-web-prod`的唯一性判断。
6. 同时读取发布审批人、窗口、回滚方案和生产验证计划。无法读取时在发版任务中分别写`未配置`和证据时间，不阻断准备发布或执行发布；原生流水线审批节点仍必须保留，不得绕过。
7. 不接受用户追加`项目`、`流水线`、`验证阈值`或`回滚目标`等字段覆盖派生结果；`需求=`仅为局部发布选择器，发现冲突时以线上正式关系为事实并阻塞。
8. 创建或复用后，回读发版任务的顶层关系、`发版任务→迭代`、`发版任务→派生需求`、`发版任务→源交付`和`发版任务→无关联单据已完成Bug`关系、受管A/B/C/D范围区块、活动生产流水线和发布控制就绪度，全部一致才算准备完成。

### 直接执行流水线

`执行测试流水线：流水线=名称`或`执行生产流水线：流水线=名称`的控制要求：

1. 命令本身授权立即启动一次，不再二次确认。
2. 在当前云效组织和当前项目上下文内按名称解析，必须唯一匹配。
3. 测试命令只允许匹配测试逻辑环境，生产命令只允许匹配生产逻辑环境。Flow原始`envName=日常环境`是定义容器字段；当活动流水线名称、Codeup代码源/分支和部署目标一致指向生产时，不视为环境冲突。
4. 显式口令按名称唯一匹配；生命周期自动节点按正式范围中的Codeup仓库、代码源和目标分支匹配，并分别要求名称带`test/测试`或`prod/生产`。先排除禁用、归档以及名称带`-old/_old/-legacy/_legacy/旧/停用/废弃/归档`的退役定义，再做唯一性判断；一个流水线覆盖多个仓库时按流水线ID去重。
5. 只启动已有定义，不允许借此创建、修改、复制、重命名或删除流水线及服务连接。
6. 单条用户消息对每条去重后的流水线最多提交一次；重新发送命令属于新的执行授权。
7. 返回新执行ID、执行链接、环境、开始时间和初始状态。
8. 跟踪到终态；运行期间每次等待不超过60秒并提供简短进度。
9. 失败时定位首个失败阶段、Job、任务和步骤，读取该步骤日志及必要上下文。
10. 启动成功不代表流水线最终成功，也不触发需求、任务或Bug状态变化。
11. 存在无默认值的必填参数时停止并返回缺失参数；不得猜测。
12. 流水线内部审批节点保持有效，不得绕过。

### 失败日志与诊断

不设置独立失败分析口令。`执行测试流水线`、`执行生产流水线`或`执行发布`监控到流水线失败终态或生产验证失败时，必须在同一命令响应中自动完成以下诊断；主动回滚或回滚流水线失败也执行相同规则。需要复查历史失败时，使用其所属发版任务执行`查询发布：发版任务=<ID>`。

日志读取顺序：

1. 官方 `aliyun devops` CLI 的 Flow/AppStack 执行详情、阶段、任务和日志命令。
2. CLI 返回的精确任务/步骤日志下载地址；仍由 CLI 身份访问并脱敏读取。
3. 若 CLI 无权限、日志过期或接口未提供，则报告限制并停止诊断，不切换浏览器通道。

必须输出：

- 流水线名称、环境、执行ID和执行URL。
- 最终状态、失败时间和持续时长。
- 首个失败阶段、Job、任务、步骤和退出码。
- 脱敏后的关键错误日志及必要上下文。
- `日志确认原因`、`可能根因`或`仅观察到的现象`三者之一。
- 影响范围、建议处理动作和是否适合重试。
- 失败类型、失败生产验证项、阈值、实际值、证据时间和证据来源（适用时）。
- 原生产执行、回滚执行、回滚前后版本、恢复验证、剩余风险和下一责任人（适用时）。

禁止输出或保存密码、Token、Cookie、AccessKey、私钥、认证头和密钥变量值。若完整日志含敏感内容，只保留脱敏片段；若不能安全脱敏，只返回定位信息和日志链接。

日志无权限、已过期、被截断、页面加载失败或接口不可用时，必须说明具体限制。不能把最后一行错误、退出码或通用`script returned exit code 1`直接当作根因。

### 状态驱动的执行发布

`执行发布：发版任务=ID`必须先读取真实状态，再按下表执行：

任何状态判断、生产执行、回滚、重新发布和产品交接前，必须先回读并校验发版任务为顶层任务，且其迭代、A类需求、多个源【交付】与无关联单据已完成Bug关系均与冻结范围一致。发版任务若是任何【交付】的`TASK_SUB`子项、关系缺失或冲突、范围不一致或任务不唯一时阻塞；对已有生产尝试的历史任务不得重挂或扩容。

| 发版任务真实状态 | 动作 |
|---|---|
| 已准备/待发布且无历史尝试 | 校验冻结范围、唯一活动生产流水线、运行参数和幂等；创建首次尝试并启动一次生产执行 |
| 发布中/执行中且当前尝试未终结 | 按`releaseAttemptId`识别当前处于生产执行还是生产验证；关联并继续跟踪，禁止再启动一条 |
| 发布失败且回滚未开始/执行中 | 核验并自动执行或接续一次回滚；禁止启动第二条回滚 |
| 发布失败且回滚已成功 | 当前尝试已终结；幂等返回回滚证据，不启动生产；转入正式修复回流，全部门禁通过后仅`重新发布`可创建下一尝试 |
| 发布完成 | 禁止重跑生产；复核证据、错误自动关闭和产品交接；若出现上线异常，只有显式`执行回滚`可进入主动回滚 |
| 已完成/已关闭 | 不执行生产；检查是否由产品验收正常关闭，异常则只报告 |
| 状态缺失、冲突或无法唯一解释 | 阻塞，不猜测 |

生产执行技术成功后自动完成：

1. 验证逻辑prod环境、唯一执行ID、发布范围和幂等；仅实际使用回调时校验回调。
2. 记录可读取的生产Tag、Commit或不可变制品摘要；读取不到时写`未获取`。
3. 执行当前可用的生产检查；只允许只读探针，或已经审批且可清理/可回滚的合成业务动作。无自动化入口的检查写`未自动验证`。
4. 可用检查记录检查ID、目标、实际值、时间、证据来源和结果；可选检查缺失或无观察窗口不阻断技术发布完成。
5. 在发版任务描述中幂等写入并回读以下受管区块；不可读取的可选字段使用明确状态，不得伪造：

```html
<!-- YUNXIAO_RELEASE_PRODUCTION_EVIDENCE_START -->
<pre>{"schemaVersion":"oneos.release-production/v1","releaseTaskId":"TASK-900","executionId":"EXEC-1","environment":"prod","pipelineStatus":"成功","scope":["REQ-1"],"immutableAnchor":"tag/commit/artifact-or-未获取","callbackVerified":"true|not_used","verificationStatus":"通过|失败|未自动验证","verificationEvidence":[],"idempotencyKey":"release-..."}</pre>
<!-- YUNXIAO_RELEASE_PRODUCTION_EVIDENCE_END -->
```

6. 生产流水线终态成功且逻辑prod环境、执行ID和冻结范围回读一致后，发版任务和本批需求进入真实`发布完成`；生产检查缺失形成风险提示，产品/业务验收继续负责最终确认。
7. 立即检查一次，等待5至30秒后再次检查是否被错误自动关闭。
8. 输出`YunxiaoPM`产品验收交接，口令必须以`发版任务`为唯一验收锚点。

生产执行或生产验证失败后自动完成：

1. 确认执行已经进入`失败`、`已取消`、`超时`或平台等价的不可继续终态，或者冻结生产验证计划中的明确失败阈值已命中；审批等待、参数缺失、登录/OTP、权限阻塞、监控不可用、证据缺失、仍在运行或状态未知不属于失败终态。
2. 抓取并脱敏首个失败步骤日志，或保存失败验证项的阈值、实际值、时间和证据来源。
3. 保存失败类型、问题现象、失败执行/验证项、影响范围和已配置回滚方案。
4. 发版任务进入真实`发布失败`。
5. 在同一`执行发布`目标中读取当前生产版本、稳定版本锚点、回滚目标、制品、权限和幂等。全部可验证时自动执行或接续一次回滚；任一缺失时写`自动回滚=false`并返回人工恢复边界。
6. 已触发回滚时跟踪终态并保存原执行ID、回滚执行ID、回滚前后版本、时间、操作者和证据。
7. 无论是否具备自动回滚条件，发版任务都保持真实`发布失败`；需求状态不凭空回退。

失败识别后必须在发版任务描述中幂等写入并回读问题区块；敏感日志只保存脱敏片段或安全链接：


### 执行发布的失败分支与自动回滚

`执行发布：发版任务=ID`同时授权在明确生产失败后执行一次已保存且可验证的回滚，不再要求独立`发布失败`口令。执行顺序：

1. 唯一解析发版任务、最近生产执行、当前生产版本和目标环境。
2. 仅接受本次生产执行已失败、取消、超时、平台明确判定不可继续，或本次冻结生产验证项明确失败的场景；已经进入`发布完成`后发现问题改用显式`执行回滚`。
3. 读取准备发布时保存的回滚方式和最后一个稳定生产Tag、Commit或制品摘要。
4. 核验回滚目标与当前版本不同、制品仍可用、权限有效且没有另一条回滚在运行。
5. 使用任务中保存的回滚流水线、回滚阶段或平台回滚动作执行一次。
6. 跟踪到终态；失败时抓取并脱敏回滚日志。
7. 回滚成功后记录原执行ID、回滚执行ID、回滚前后版本、时间、操作者和证据。
8. 发版任务保持真实`发布失败`；需求状态不凭空回退。恢复稳定后固定输出YunxiaoQA的`接收发布回流`口令，不再以“由负责人决定”作为无口令终点。
9. 回滚已经成功时按幂等成功返回，不重复执行。

### 上线异常的主动回滚

规范入口：

```text
$yunxiao-release-operations
执行回滚：发版任务=TASK-900 原因=<问题现象> 证据=<ID或URL>
```

该命令仅处理已经技术部署或进入`发布完成`、但尚未由产品验收关闭的发版任务：

1. 三个字段必须齐全；按ID唯一读取发版任务，不接受需求ID或流水线执行ID替代。
2. 验证证据来源可审计，且时间、prod环境、发布范围和当前版本与本次发版一致。聊天转述、无时间截图或无法定位范围的描述不能单独作为失败证据。
3. `已完成/已关闭`生命周期禁止重开；交回`YunxiaoPM`建立线上缺陷、热修复和重新发布生命周期。
4. 读取原先冻结的回滚方案、稳定版本、制品、权限和幂等记录；命令参数不得覆盖回滚目标或扩大范围。
5. 写入问题证据并尝试将任务推进到项目真实`发布失败`；状态模型不支持时保留实际状态并记录不一致，但不得伪造近义状态。
6. 执行或接续唯一一次回滚，监控终态；成功后执行冻结的恢复健康检查和最小业务验证。
7. 回滚成功后保持真实失败结论，不自动重发、不回退需求业务状态；回滚失败时保留现场并禁止自动重试。
8. 输出问题类型、现象、时间线、影响、证据、诊断置信度、原执行、回滚执行、前后版本、恢复验证、剩余风险、责任人和下一动作。

出现以下任一情况时不执行：

- 找不到唯一生产执行、环境或发版任务。
- 没有明确回滚方案或稳定版本锚点。
- 目标制品不存在、已过期或无法验证。
- 另一条回滚正在运行。
- 回滚已经成功。
- 需要登录批准、OTP、权限提升或流水线内部审批尚未完成。

回滚门禁失败时仍保留真实发布失败状态和全部失败证据，但不猜测回滚目标、不创建临时回滚方案，也不要求用户输入另一条`发布失败`命令；直接报告缺失条件和人工恢复路径。

### 修复回流后的重新发布

规范入口：

```text
$yunxiao-release-operations
重新发布：发版任务=TASK-900 回归证据=<ID或URL>
```

必须同时满足：

1. 发版任务存在同一范围的生产失败事件或`oneos.product-acceptance/v1`不通过证据，且生命周期未被产品关闭。
2. 原迭代、执行任务和需求范围保持唯一；命令不得更换迭代或增删需求。
3. 受影响Bug均为已关闭，并提供当前回归证据ID或URL；不要求固定的QA、test部署或逐Bug JSON schema。
4. 当前生产状态可唯一读取且不存在仍在运行的旧生产或回滚执行。
5. 回滚、fix-forward、test部署、审批、窗口、制品和生产检查信息有则记录；缺失时明确风险和`自动回滚=false`，不阻断显式重新发布。

通过后以当前最大尝试号加一，生成`attemptType=re_release`、新的`releaseAttemptId`、`previousAttemptId`和幂等键，保留旧生产、失败、回滚、验收和修复证据，按`发布失败|发布完成且验收不通过→发布中`执行新的生产流水线。任何旧执行ID或产品验收证据不得复用；可用生产检查重新记录，缺失时标记`未自动验证`。

重新成功后再次进入`发布完成`并输出新的产品验收口令；失败仍走同一自动回滚和修复回流，不创建第二套发版任务。

`查询发布`只支持`查询发布：发版任务=<ID>`。按发版任务正式关系统一返回需求范围、流水线执行ID、失败日志、回调幂等、错误自动关闭和下一动作。需求ID和流水线执行ID只作为返回证据，不得作为查询入口。它永远只读。

## 5. 发布任务

`【发版】`任务必须：

1. 标题精确前缀。
2. 正式关联一个精确迭代。
3. 正式关联从该迭代A/B/C/D分类派生的本批A类需求。
4. 本批需求均测试完成。
5. 迭代、发版范围和受管范围哈希一致；测试计划与其他QA材料有则记录。
6. 有唯一活动生产流水线；负责人、审批、窗口、回滚方案和生产验证计划允许标记为`未配置`，不得伪造为已就绪，也不得因此阻断正常首次发布。

查重键：

```text
项目ID + 迭代ID + 排序后的A类需求ID + release_prepare
```

存在多条无法区分的发版任务时停止，不自动选最新。

## 6. 发布成功和失败

成功门禁：

```text
环境 = prod
且 执行ID唯一
且 流水线实际成功
且 发布范围覆盖本批需求
且 当前状态允许
且 幂等回读有效
且 仅在实际使用回调时回调签名/时间戳有效
```

满足后才推进到发布完成并停留，通知产品验收。

失败门禁：核查真实失败执行、阶段、原因和范围，进入项目真实发布失败状态。项目没有该状态时记录阻塞，不创建近义状态。

## 7. 运维负向测试

| 场景 | 期望 |
|---|---|
| test部署成功 | 不进入发布完成 |
| 本批存在未测试完成需求 | 不进入发布中 |
| 迭代含正式延期或尚未测试完成的需求 | 分类为B，记录但不阻塞、不进入本批 |
| 已测试完成的自动候选或局部发布显式选入项测试/证据未完成 | 分类为C，准备发布零写入 |
| QA证据未带迭代、迭代与发布命令不一致或正常需求没有test部署 | 记录为测试信息缺口，不阻断准备发布 |
| 选入需求跨项目/跨迭代/关系冲突 | 分类为D，准备发布零写入 |
| 迭代名称不存在或不唯一 | `准备发布`零写入并返回候选 |
| 迭代与A类需求跨项目或跨迭代 | 阻塞，不按标题猜测 |
| 用户在准备发布中追加项目、流水线或与线上关系冲突的需求范围 | 忽略手工覆盖并阻塞，返回线上真实关系 |
| 同仓库/分支同时存在`oneos-web-prod`和`oneos-web-prod-old` | 忽略`*-old`退役定义，以唯一活动流水线`oneos-web-prod`继续 |
| 活动prod流水线的Flow原始环境显示`日常环境`，但名称、代码源/分支和部署目标均指向生产 | 记录原始环境和`logicalReleaseEnvironment=prod`，不阻断 |
| 准备发布或执行发布时审批人、窗口、回滚方案或生产验证计划缺失 | 在发版任务中逐项写`未配置`，不阻断；保留流水线原生审批，缺少回滚时写`自动回滚=false` |
| 已冻结发版范围与本次重新分类结果不一致 | 阻塞，不静默扩容或缩减 |
| 发版任务混入其他迭代需求 | 阻塞 |
| 错误签名/过期时间戳/重复执行ID | 不写状态 |
| 生产流水线成功但范围不匹配 | 阻塞 |
| 生产流水线成功但生产验证未执行或证据缺失 | 记录`未自动验证`和风险提示；环境、范围与执行ID一致时进入发布完成并交产品验收 |
| 冻结的生产验证项明确失败且回滚门禁通过 | 进入发布失败，同一`执行发布`自动启动一次回滚并反馈问题 |
| 监控不可用、探针无权限或结果未知 | 视为阻塞而非失败；不触发回滚，除非冻结计划明确把该可观测条件定义为失败 |
| 发布完成后自动关闭 | 判定误触发并保护验收门禁 |
| `重新发布`未获批准或修复证据不全 | 不开始新生产尝试；已经启动的回滚仍按幂等状态接续 |
| 生产执行明确失败且回滚门禁通过 | 同一`执行发布`自动启动一次回滚并跟踪 |
| 流水线等待审批、缺参数、登录/OTP、权限不足、仍在运行或状态未知 | 不误判失败，不触发回滚 |
| 回滚方案、目标版本或制品无法唯一确定 | 不执行回滚 |
| 回滚已经运行或成功 | 接续监控或幂等返回，不重复启动 |
| 回滚失败 | 保留日志和现场，禁止自动重试 |
| 发布/验收失败后直接重复`执行发布` | 不重试；返回`接收发布回流`或`重新发布`所缺证据 |
| 首次尝试监控中断或仍在执行/验证中，再次输入`执行发布` | 按原`releaseAttemptId`接续；不创建新尝试、不启动第二条生产执行 |
| 首次或重发尝试已明确失败，即使代码已修复且重新审批后再次输入`执行发布` | 仍不构成重试授权；零生产执行，要求完整修复回流后使用`重新发布` |
| `重新发布`再次失败后改用普通`执行发布` | 零生产执行；完成下一轮修复回流后再次使用`重新发布`并递增尝试号 |
| `重新发布`缺少当前回归证据、受影响Bug仍未关闭或原范围发生变化 | 零生产执行，保持失败/待修复状态；不要求固定QA/test部署/逐Bug JSON格式 |
| 发布完成后出现有证据的业务异常并显式执行回滚 | 核验任务未被产品关闭及同一回滚门禁；执行一次主动回滚并反馈问题 |
| 已完成/已关闭后要求回滚 | 不重开旧生命周期；交回YunxiaoPM建立线上缺陷/热修复流程 |
| 主动回滚仅有聊天转述、无时间截图或证据与本次范围不一致 | 零执行并返回证据缺口 |
| 排除退役定义后活动流水线名称不存在或仍有多条 | 不执行，返回匹配问题 |
| 测试命令匹配到生产环境或生产命令匹配到测试环境 | 不执行 |
| 流水线需要无默认值参数 | 不执行，返回所需参数 |
| 执行失败但日志不可读取 | 返回执行ID、失败步骤、权限或保留期限制，不猜测根因 |
| 日志包含密钥或认证信息 | 脱敏后返回，不能安全脱敏时不输出原文 |

## 8. 运维交付给产品

必须提供：项目/迭代、A类本批需求、B类延期需求、C/D为空证据、发版任务顶层回读、正式关系、范围哈希、生产流水线、逻辑环境、执行ID、开始/完成时间、发布范围、终态成功和幂等回读。生产版本锚点、回调校验、生产检查、观察窗口和回滚状态有则提供，缺失时明确写`未获取/未使用/未自动验证/未配置`。下一口令为`$YunxiaoPM`加`验收通过：发版任务=<ID>；验收人=<人>；证据=<ID或URL>`。
