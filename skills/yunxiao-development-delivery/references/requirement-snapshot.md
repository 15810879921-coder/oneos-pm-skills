# 开发需求快照

开发需求快照是`分配任务`在技术方案之前固化的任务级索引。它不是新的需求源，也不能替代 PRD 或原型；它用于证明本次开发读了哪些产品材料、当前任务覆盖什么、技术方案依据哪个版本生成。

## 1. 生成顺序

1. 用`yunxiao_cli_allocate_task.py analyze`读取唯一关联需求、交付关系和完整描述。
2. 优先读取 PM 在需求或【交付】中留下的产品交棒快照，包括 PRD/原型入口、版本指针、变更范围和页面/交互索引；产品快照是产品修改后的版本印记。
3. 只裁剪当前开发任务涉及的端、章节、页面、状态和规则，生成任务级开发需求快照。历史交棒没有产品快照时，才从交付描述、需求正文、附件和明确引用的权威材料兼容补录，并写明`快照来源：历史补录`；不能冒充 PM 确认版本。
4. 基于任务快照生成技术实施方案。方案必须写入任务快照 SHA-256。
5. 将两个文件一并传给分配适配器，经过带哈希的`preflight → apply → read-back`写入开发任务。

产品快照只认`ONEOS_PRODUCT_HANDOFF_SNAPSHOT_START id=ps-... sha256=...`受管标识。需求与【交付】两边编号/哈希一致才视为 PM 快照有效；两边都没有时走历史补录；只缺一边或哈希不一致表示产品写入不完整，阻断本次分配并交回 YunxiaoPM 执行`刷新产品快照`，不得自行选一边。

优化需求没有原型时，直接基于云效完整描述生成快照。需求描述为空时，`analyze`只报告材料缺口，不提前卡死；继续从交付描述、附件和明确引用中寻找权威交棒材料，只有验收关键内容最终仍无法取得时才阻断受影响范围。历史开发任务没有快照时，`开始开发`先按上述只读链路补生成；缺快照本身不作为僵硬拒绝门禁。

## 2. 内容模板

```markdown
# 开发需求快照：<需求编号> <需求标题>

## 任务目标
<本次要解决的问题和预期结果>

## 本次范围
- 做：...
- 不做：...
- 端/交付范围：Web | 小程序 | 后端 | 全栈 | 未定义

## 页面与交互
<页面、入口、关键状态和交互；不适用时写未定义>

## 业务规则
<字段口径、状态、角色权限、正向流程、异常与边界；不存在时写未定义>

## 验收条件
<可验证条件及对应来源；缺失时明确受影响范围>

## 来源与版本
- 云效需求：<编号、gmtModified、描述哈希>
- 原型/PRD：<URL或文件、读取时间、内容哈希或可得版本指针>
- 产品交棒快照：<编号/哈希；历史无快照时写无>
- 快照来源：PM产品快照裁剪 | 历史补录
- 冲突/风险：无 | <清单>
```

必须绑定正式需求编号。不得包含 Skill 选择器、执行口令、未经证实的仓库路径、文件名或接口字段。

## 3. 材料职责与冲突

- 云效编号、状态和关系：生命周期身份。
- PRD/Markdown：业务规则、字段口径和验收标准。
- 原型：页面结构、文案、交互和视觉状态。
- 源码清单、演示代码、现有仓库：实现线索和当前事实，不能补造业务决定。

业务规则与验收关键内容缺失或冲突时，只阻断受影响范围；纯视觉图片、辅助链接或非本任务章节不可读时记录风险，不阻断快照和分配。

## 4. 开始开发时的新鲜度

- 快照来源版本未变化：只精读本任务涉及的 PRD 章节、页面和交互状态，不重读整套原型和数万字 PRD。
- PM 产品交棒快照版本变化：重新裁剪任务快照；随后刷新绑定旧任务快照哈希的技术方案。
- 快照显示技术方案漏项：先补技术方案再开工。
- 只拿不到哈希但仍能完整读取材料：保留 URL/附件 ID、读取时间和内容长度后继续，不把“无哈希”单独设为门禁。

快照新鲜度以`来源与版本`中的权威来源指针为准，不以聊天摘要或旧截图为准。
