# 生产后产品验收

## 口令

```text
$YunxiaoPM
拉取待验收需求：发版任务=TASK-900

$YunxiaoPM
验收通过：发版任务=TASK-900；验收人=王经理；证据=ACCEPTANCE-ID或URL

局部验收：发版任务=TASK-900；验收人=王经理；证据=ACCEPTANCE-ID或URL；范围清单=<JSON文件>

$YunxiaoPM
验收不通过：发版任务=TASK-900；验收人=王经理；原因=...；证据=ID或URL
```

`发版任务`是唯一锚点；不接受单个需求编号替代，不按标题猜范围。

未给`范围清单`时默认验收发版冻结清单全部范围。给出时，每项必须含`deliveryUnitId、componentId、deploymentTargetId、productionVersion`，可选`branchInstanceIds`；脚本只向发版任务追加该组件/目标的`ACCEPTED`事件并输出分支清理候选，不把整批需求、交付或发版任务推进完成。其余组件保持`PENDING_ACCEPTANCE`。同一分支仍承载未验收范围时只能成为组件候选，不能删除分支。

## 通过门禁

1. 发版任务唯一且状态=`发布完成`。
2. 本批需求全部=`发布完成`（验收通过时亦允许已完成/已关闭续跑）；范围可由 **发版→需求** 或 **发版→【交付】→需求** 解析，不要求发版任务描述含 `oneos.release-production/v1` 生产证据区块。
3. 每个需求对应唯一源`【交付】`，交付保持=`处理中`（通过续跑允许已完成）。
4. 发版任务关联的无交付已完成Bug全部与发版迭代一致、已处于`已完成|已关闭`、具有独立复测证据，且只回读验收证据、不再次流转状态。
5. 验收人、证据非空，证据对应本批验收范围。
6. 整批通过从完整解析后的源【交付】读取唯一迭代（只有独立Bug时读取Bug迭代），再以官方 `projex-get-sprint` 回读来源名称、端别、起止日期和负责人。仅在工作项无法回读迭代时允许用`--source-sprint-id`补充，若已知迭代与显式值不一致则停止。已确认来源不是可解析的 Web 版本迭代时保留原验收并在Plan明确`skippedNonWeb`，不补建；无法定位来源时明确`unresolved/missing_source`并要求补来源信息，禁止把未知来源写成非 Web。
7. 先dry-run并经YunxiaoPM Plan确认。Plan 同时列出关闭动作、冻结来源迭代和连续两期子版本补建动作；本次验收确认同时覆盖这些动作，不再二次确认。

执行入口：

```powershell
skill-run accept_release.py pass `
  --release-id <云效内部ID> `
  --release-sn TASK-900 `
  --acceptor '王经理' `
  --evidence 'ACCEPTANCE-ID-or-URL' `
  --dry-run
```

若官方工作项详情未返回迭代，再追加`--source-sprint-id <本批来源迭代内部ID>`；不得用任意 Web 迭代覆盖已知的批次迭代。

局部验收增加`--scope-file <JSON>`；先dry-run再执行。局部验收不流转工作项状态，全部范围验收仍按原流程收口。

去掉`--dry-run`后，脚本通过官方 `aliyun devops` CLI 向发版任务、每条需求、每个源【交付】和本批无交付已完成Bug写入同一`oneos.product-acceptance/v1`验收区块并回读，再依次推进源`【交付】处理中→已完成`、本批需求`发布完成→已完成`、发版任务`发布完成→处理中→已完成`。无交付已完成Bug只写证据并回读，不改变其已完成状态。每个对象均通过官方工作流读取状态ID，不使用本地硬编码ID。

只有上述必要关闭全部回读成功后，脚本才按dry-run冻结计划创建后两期空 Web 迭代。版本只在来源版本最后一位连续加一两次，周期和负责人沿用来源迭代；已存在的目标迭代仅在名称、端别、起止日期、负责人全部精确且同名唯一时复用。该动作不挂需求或交付，不创建开发/测试任务，不修改任何旧迭代日期或负责人。

补建失败不改变验收成功结论，也不回滚已完成关闭；输出 `acceptanceOk=true`、`followupSprints.apply.ok=false`、`resumable=true` 和冻结计划路径，并以退出码4提示从同一计划续跑。禁止改用实时最高 Web 版本重新生成目标。

## 验收不通过

```powershell
skill-run accept_release.py fail `
  --release-id <云效内部ID> `
  --release-sn TASK-900 `
  --acceptor '王经理' `
  --evidence 'ACCEPTANCE-ID-or-URL' `
  --reason '验收失败原因' `
  --dry-run
```

确认后向发版任务、需求、源交付和本批无交付已完成Bug写入并回读统一“不通过”证据；尝试把发版任务从`发布完成`转到项目真实`发布失败`，若流程不支持则保留实际状态并在证据中标记`notSupported`。需求与源交付保持真实状态，无交付已完成Bug不回退，不得伪装为生产流水线失败，也不得擅自回退需求。

无论状态迁移是否受项目流程支持，下一步都固定输出：

```text
$YunxiaoQA
接收发布回流：发版任务=TASK-900；触发=产品验收失败；证据=ID或URL
```

后续必须经过正式缺陷、开发修复、test部署、逐Bug复测和回归证据，再由发布Skill执行`重新发布`；不得直接再次验收或直接重跑生产。

## 幂等与部分失败

- 原整批验收幂等键保持=`发版任务内部ID + 验收结论 + 验收证据`，避免旧版已写证据的半途任务无法续跑；局部验收另加范围哈希。来源迭代与两期目标绑定在带哈希的冻结补建计划中，不改变原验收键。
- 重试只替换同一受管验收区块，保留人工描述。
- 首次执行先把同一验收幂等键写入发版任务、全部需求、全部源交付和无交付已完成Bug，再逐项流转；任一状态写入失败时停止并逐项报告真实状态。
- 续跑允许需求处于`发布完成|已完成`、源交付处于`处理中|已完成`、无交付Bug保持项目完成态、发版任务处于`发布完成|已完成`；已经完成的对象必须带同一验收幂等键，否则拒绝接续。
- 重试只流转尚未完成的需求、源交付和发版任务；无交付Bug只回读证据，禁止用浏览器补点剩余对象。
- 发版任务已完成时，只有全部需求、源交付、无交付已完成Bug和验收证据均一致才按幂等成功返回。
- 后两期目标、日期和来源ID写入本地持久预检文件并带哈希；重复验收或关闭后续跑只读取该冻结文件。第一期已创建而第二期失败时，精确复用第一期并继续第二期；不得从实时最高版本再新增两期。
- `--scope-file`局部通过、`fail`不通过、已确认非 Web/非版本来源、来源未解析、关闭尚未全部成功以及任何验收前置失败均不应用补建计划、不会创建云效迭代；只读预检可提前留下冻结计划供同批续跑。已确认非 Web 整批仍照常完成原验收并显式报告`skippedNonWeb`，来源未解析则报告`unresolved/missing_source`和所需补充信息。
