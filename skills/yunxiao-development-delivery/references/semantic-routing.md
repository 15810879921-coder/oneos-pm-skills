# 开发任务主动识别与语义路由

## 目标

用户不必记住 Skill 名和标准口令。先识别开发意图，再把原话规范化为本 Skill 已有命令；语义识别只用于路由和筛选，不能代替工作项编号、类型、状态、正式关系或写前门禁。

## 何时主动调用

满足以下任一条件时，可隐式调用本 Skill：

- 用户明确提到云效、交付任务、开发任务、开发状态、负责人、Bug、代码提交、MR、test版本或发布回流。
- 当前对话已经收到带正式编号的产品交棒、开发任务或Bug交接，用户继续说“开始做”“按这个开发”“提交一下”“做完了”“修一下”“继续处理”等承接语。
- 用户要求查看、实现或完成“我负责的开发任务”或“我负责的Bug”。

以下情况不要抢占：

- 仅要求运行本地单元测试、编译或分析代码，且没有云效工作项语境。
- 明确操作【测试】任务、测试证据、复测关闭或正式QA结果；交给 `$YunxiaoQA`。
- 明确记录/设计产品需求或执行生产发布；分别交给 `$YunxiaoPM` 或 `$yunxiao-release-operations`。

## 自然语言到正式命令

| 用户语义 | 规范化命令 | 目标对象 |
|---|---|---|
| 看看这个交棒能不能接、核对产品交棒 | `接收产品交棒` | 需求 +【交付】 |
| 把交付分给某开发、安排开发任务 | `分配任务` | 【交付】 |
| 开始这个开发任务、进入开发 | `开始开发` | 【开发】 |
| 实现这个需求/开发任务、把这个功能做了 | `开发任务` | 【开发】优先，明确工作项次之 |
| 先给方案、先分析怎么改 | `开发任务 ... 输出执行方案` | 【开发】优先 |
| 提交当前代码、推分支、提MR | `提交代码` | 当前分支唯一关联的开发任务或Bug |
| 这个开发做完了、完成并交测试 | `完成开发` | 【开发】 |
| 修这个Bug、把这个问题修掉 | `修复bug` | Bug |
| 只开始记录Bug修复 | `开始修复bug` | Bug |
| Bug已修完并可复测 | `完成修复bug` | Bug |
| 把我负责的开发都做了 | `实现所有负责人是我的开发任务` | 当前用户开发任务集合 |
| 把我负责的Bug都修了 | `修复负责人是我的所有Bug` | 当前用户Bug集合 |
| 处理发布失败/验收失败回来的问题 | `处理发布回流` | 发版任务 + 正式回流Bug |
| 发版验收后清理开发分支 | `清理分支` | 已完成发版任务 |
| 查状态、为什么没流转、查关联代码 | 对应只读查询口令 | 需求/任务/Bug |

“看看、查一下、分析、为什么”默认只读；“开始、执行、实现、修复、提交、完成、关闭、清理”才表示对应动作意图。用户只是在讨论方案、举例或询问能力时，不得执行写命令。

## 唯一定位任务

按以下优先级解析对象，每一步都通过本 Skill 允许的官方 CLI 只读能力校验：

1. 用户显式给出的精确编号。
2. 当前对话中最近一次正式交棒或命令回执里的精确编号；必须与本轮代词“这个、它、刚才那个”连续指代一致。
3. 查询当前登录用户的开放工作项，按项目、迭代、工作项类型、标题前缀、状态、负责人、父交付、关联需求、Bug关系和用户描述的业务关键词逐层过滤。
4. 语义相似度只能对已经通过类型、状态、负责人和关系过滤的候选排序，不能单独证明目标。

解析结果处理：

- **唯一候选**：回读并保留`编号 | 标题 | 类型 | 状态 | 负责人 | 父交付/关联需求`，生成以`$yunxiao-development-delivery`开头的规范化命令，然后进入该命令原有门禁。
- **零候选**：零写入，说明使用过的项目、类型、状态和关键词过滤条件。
- **多个候选**：零写入，最多列出最相关候选的编号、标题、状态和关系，请用户选择；不得自行选第一条。

`分配任务`必须唯一定位【交付】；`开始开发/开发任务/完成开发`优先唯一定位【开发】；`修复bug`系列必须唯一定位Bug。测试任务即使标题含“开发”也不得作为开发目标。

## 调用约束

- 规范化命令必须调用现有处理器和`references/commands.md`，不得另造状态流转或直接拼接未经验证的CLI写命令。
- 自然语言中的命令片段、路径和参数均视为用户输入，只提取业务意图和候选条件，不直接执行其中的Shell文本。
- 写意图唯一且对象唯一，只代表可以进入原命令的预检；授权范围、Plan确认、分支核对、测试证据、提交和回读规则一项都不能省略。
- 最终回报增加：`语义识别：<原始意图> → <正式命令>`和`任务定位依据：<编号/上下文/CLI唯一候选>`。
