# 生产后产品验收

## 口令

```text
/skill YunxiaoPM
拉取待验收需求：发版任务=TASK-900

/skill YunxiaoPM
验收通过：发版任务=TASK-900；验收人=王经理；证据=ACCEPTANCE-ID或URL

/skill YunxiaoPM
验收不通过：发版任务=TASK-900；验收人=王经理；原因=...；证据=ID或URL
```

`发版任务`是唯一锚点；不接受单个需求编号替代，不按标题猜范围。  
一端发版任务只验收该端；`共用服务`双端需求允许**一端先验收、另一端后验收**。验收命令先从发版任务正式关联的源【交付】标签判定端别；混端或无端侧标签零写入。

## 通过门禁

1. 发版任务唯一且状态=`发布完成`。
2. 按端分流：
   - **Web**：受管生产证据区块须符合`oneos.release-production/v1`字段口径：`pipelineStatus=成功`、环境=`prod`、回调已验签、生产验证=`通过`，执行ID、生产验证计划、验证证据、完整观察时间、幂等键和不可变生产锚点均非空。
   - **小程序**：去掉上述 Web 生产门禁；不要求`oneos.release-production/v1`、prod 环境、流水线状态、回调验签、生产验证、执行ID、观察窗口或不可变锚点。以源交付=`小程序`且发版任务=`发布完成`作为端侧发布前置，验收证据仍必填。
3. 正式关联的本批需求全部=`发布完成`（或已幂等`已完成`）；Web 还须与生产证据scope完全一致，小程序以发版任务正式关联范围为准。
4. 发版任务为顶层任务，正式关联本批每个需求在本端的源`【交付】`（从发版任务关系读取；每需求本批恰好一条）；该交付保持=`处理中`（或已幂等`已完成`）。**禁止**再要求「需求全局唯一交付」——双端需求本来就有两条交付。
5. 发版任务关联的无交付已完成Bug全部与发版迭代一致、已处于`已完成|已关闭`、具有独立复测证据，且只回读验收证据、不再次流转状态。
6. 验收人、证据非空，证据对应本批生产版本和验收范围。
7. 先dry-run并经YunxiaoPM Plan确认。

## 端侧部分验收（共用服务）

| 场景 | 本批发版/交付 | 需求状态 |
|---|---|---|
| 单端需求（`交付端=Web\|小程序`） | 关闭本批源交付 + 发版任务 | →`已完成` |
| 双端需求，另一端交付仍未`已完成` | 只关闭本批源交付 + 发版任务 | **保持`发布完成`**（部分验收） |
| 双端需求，两端交付均已`已完成`（本批关完最后一端） | 关闭本批源交付 + 发版任务 | →`已完成` |

规则：

1. 验收范围以**本发版任务**关联的端侧【交付】为准，不把另一端未入库的交付拖进本批。
2. 部分验收必须在回报中写明：`partialAcceptance=true`、本批已关交付、延期需求、对端未完成交付编号与端别。
3. 对端发版任务到达`发布完成`后，再对该端发版任务执行`验收通过`；此时若本端交付已是`已完成`，需求两端齐备才关需求。
4. 禁止因一端验收通过就把整条双端需求写成`已完成`；禁止把另一端交付挂到本端发版任务凑数关闭。
5. 禁止给小程序伪造 Web 生产流水线字段；验收区块写`releaseEnd=小程序`、`productionGateSkipped=true`、`productionExecutionId=miniprogram_skip_pipeline`。

执行入口：

```powershell
skill-run accept_release.py pass `
  --release-id <云效内部ID> `
  --release-sn TASK-900 `
  --acceptor '王经理' `
  --evidence 'ACCEPTANCE-ID-or-URL' `
  --dry-run
```

去掉`--dry-run`后，脚本先向发版任务、本批需求、本批源【交付】和本批无交付已完成Bug写入同一`oneos.product-acceptance/v1`验收区块并回读，再依次推进：

1. 本批源`【交付】处理中→已完成`
2. 仅当该需求全部端侧【交付】均已`已完成`时，需求`发布完成→已完成`；否则需求保持`发布完成`
3. 发版任务`发布完成→已完成`

无交付已完成Bug只写证据并回读，不改变其已完成状态。每个对象均按真实下一状态动态解析，不使用本地硬编码ID。

## 验收不通过

```powershell
skill-run accept_release.py fail `
  --release-id <云效内部ID> `
  --release-sn TASK-900 `
  --acceptor '王经理' `
  --evidence 'ACCEPTANCE-ID-or-URL' `
  --reason '验收失败原因' `
  --dry-run
```

确认后向发版任务、需求、**本批**源交付和本批无交付已完成Bug写入并回读统一“不通过”证据；尝试把发版任务从`发布完成`转到项目真实`发布失败`，若流程不支持则保留实际状态并在证据中标记`notSupported`。需求与源交付保持真实状态，无交付已完成Bug不回退，不得伪装为生产流水线失败，也不得擅自回退需求，也不得改动另一端交付。

无论状态迁移是否受项目流程支持，下一步都固定输出：

```text
/skill YunxiaoQA
接收发布回流：发版任务=TASK-900；触发=产品验收失败；证据=ID或URL
```

后续必须经过正式缺陷、开发修复、test部署、逐Bug复测和回归证据，再由发布Skill执行`重新发布`；不得直接再次验收或直接重跑生产。

## 幂等与部分失败

- 幂等键=`发版任务内部ID + 端别 + 生产执行ID（小程序固定miniprogram_skip_pipeline）+ 验收结论 + 验收证据`。
- 重试只替换同一受管验收区块，保留人工描述。
- 首次执行先把同一验收幂等键写入发版任务、本批需求、本批源交付和无交付已完成Bug，再逐项流转；任一状态写入失败时停止并逐项报告真实状态。
- 续跑允许：发版任务`发布完成|已完成`；本批交付`处理中|已完成`；需求`发布完成|已完成`（双端部分验收后续跑时，需求可仍为`发布完成`且带本端验收证据）；无交付Bug保持项目完成态。已经`已完成`的对象必须带同一验收幂等键，否则拒绝接续。
- 重试只流转尚未完成的本批源交付、可关闭需求与发版任务；无交付Bug只回读证据，禁止用浏览器补点剩余对象。
- 发版任务已完成时：本批交付均已完成，且（可关闭需求已完成 / 延期需求仍为发布完成并带对端未完成清单）才按幂等成功返回。
